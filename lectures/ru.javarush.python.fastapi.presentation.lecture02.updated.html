Лекция 2: REST, полный CRUD и асинхронность в FastAPI

На первой лекции мы собрали минимальный Products API: научились запускать FastAPI-приложение, принимать path/query/body-параметры, описывать данные через Pydantic и проверять API в Swagger UI.

Теперь превращаем этот учебный API в более цельный REST-интерфейс: разберем ресурсы, HTTP-методы, статус-коды, полное обновление через PUT, частичное обновление через PATCH, удаление через DELETE и базовую асинхронную модель FastAPI.

База данных пока не подключается намеренно. Мы продолжаем использовать in-memory-хранилище, чтобы отделить тему HTTP API от темы SQLAlchemy, миграций и транзакций.

Стартовая точка

Работаем с тем же ресурсом Product. Берем решение практики первой лекции: модели, словарь вместо базы данных, базовые эндпоинты, поле category и фильтры category/only_available.

from typing import Annotated

from fastapi import FastAPI, HTTPException, Path, Query, status
from pydantic import BaseModel, Field

app = FastAPI(title="Products API", version="1.0.0")


class ProductCreate(BaseModel):
    name: str = Field(min_length=3, max_length=80)
    category: str = Field(min_length=2, max_length=40)
    price: float = Field(gt=0)
    description: str | None = None
    is_available: bool = True


class ProductRead(ProductCreate):
    id: int


products_db: dict[int, ProductRead] = {
    1: ProductRead(id=1, name="Keyboard", category="electronics", price=99.0),
    2: ProductRead(id=2, name="Mouse", category="electronics", price=49.0),
}
next_product_id = 3

В этой лекции мы не повторяем установку, базовый запуск, простые path/query-параметры и основы Pydantic. Они уже были введены в первой лекции.

REST: ресурс и операция

В REST-подходе API строится вокруг ресурсов. Ресурс — это сущность предметной области, с которой работает клиент: товар, пользователь, заказ, комментарий.

URL Что означает Пример
/products коллекция товаров получить список или создать товар
/products/{product_id} конкретный товар получить, заменить, частично обновить или удалить

Метод HTTP описывает действие, а URL описывает объект действия. Поэтому лучше GET /products/10, а не GET /getProduct?id=10.

Правило

В URL обычно используют существительные во множественном числе: /products, /users, /orders. Действие уже выражается HTTP-методом.

HTTP-методы в CRUD

CRUD — это базовый набор операций над ресурсом: create, read, update, delete. В HTTP API они обычно выражаются так:

CRUD HTTP URL Смысл
Create POST /products создать новый товар
Read list GET /products получить список товаров
Read detail GET /products/{id} получить один товар
Replace PUT /products/{id} полностью заменить товар
Partial update PATCH /products/{id} обновить только переданные поля
Delete DELETE /products/{id} удалить товар

GET должен быть безопасным: он не должен менять данные. PUT и DELETE обычно делают идемпотентными: повтор одинакового запроса приводит к тому же итоговому состоянию ресурса.

Статус-коды

Статус-код — часть контракта API. Клиент должен понимать результат не только по JSON-телу, но и по HTTP-статусу.

Код Когда использовать Пример
200 OK успешное чтение или обновление с телом ответа GET, PUT, PATCH
201 Created ресурс создан POST /products
204 No Content успешно, но тело ответа не возвращается DELETE /products/{id}
400 Bad Request запрос синтаксически валиден, но бизнес-правило нарушено нельзя применить действие к ресурсу
404 Not Found ресурс не найден нет товара с таким ID
409 Conflict конфликт с текущим состоянием данных товар с таким именем уже существует
422 Unprocessable Entity ошибка валидации FastAPI/Pydantic цена меньше или равна нулю

Если у эндпоинта статус 204, тело ответа возвращать не нужно. Это частая ошибка в учебных API: написать 204 и одновременно вернуть JSON.

POST: создание товара

POST /products создает новый ресурс внутри коллекции. ID назначает сервер.

@app.post(
    "/products",
    response_model=ProductRead,
    status_code=status.HTTP_201_CREATED,
    tags=["products"],
)
def create_product(product_data: ProductCreate):
    global next_product_id

    product = ProductRead(id=next_product_id, **product_data.model_dump())
    products_db[next_product_id] = product
    next_product_id += 1

    return product

Почему 201: запрос создал новый ресурс. Почему возвращаем ProductRead: клиенту нужен ID созданного товара и итоговое состояние ресурса.

GET: список и деталка

GET /products возвращает коллекцию. Query-параметры не меняют данные, а только уточняют чтение: поиск, фильтр, лимит.

@app.get("/products", response_model=list[ProductRead], tags=["products"])
def list_products(
    search: Annotated[str | None, Query(min_length=2, max_length=50)] = None,
    category: Annotated[str | None, Query(min_length=2, max_length=40)] = None,
    only_available: bool | None = None,
    limit: Annotated[int, Query(ge=1, le=100)] = 10,
):
    products = list(products_db.values())

    if search is not None:
        products = [
            product for product in products
            if search.lower() in product.name.lower()
        ]

    if category is not None:
        products = [
            product for product in products
            if product.category.lower() == category.lower()
        ]

    if only_available is not None:
        products = [
            product for product in products
            if product.is_available == only_available
        ]

    return products[:limit]

Для чтения одного ресурса используем GET /products/{product_id}. Если ресурса нет, возвращаем 404.

@app.get("/products/{product_id}", response_model=ProductRead, tags=["products"])
def get_product(
    product_id: Annotated[int, Path(ge=1, description="ID товара")]
):
    product = products_db.get(product_id)
    if product is None:
        raise HTTPException(
            status_code=status.HTTP_404_NOT_FOUND,
            detail="Товар не найден",
        )
    return product

PUT: полная замена

PUT используется, когда клиент присылает полное новое состояние ресурса. Если поле не пришло, оно не "остается как было", а берется из модели по умолчанию или считается отсутствующим.

@app.put("/products/{product_id}", response_model=ProductRead, tags=["products"])
def replace_product(
    product_id: Annotated[int, Path(ge=1, description="ID товара")],
    product_data: ProductCreate,
):
    if product_id not in products_db:
        raise HTTPException(
            status_code=status.HTTP_404_NOT_FOUND,
            detail="Товар не найден",
        )

    product = ProductRead(id=product_id, **product_data.model_dump())
    products_db[product_id] = product

    return product

Пример: если у товара было описание, а клиент отправил PUT без описания, описание станет None. Это ожидаемое поведение полной замены.

PATCH: частичное обновление

PATCH используется, когда клиент хочет изменить только часть полей. Для этого нужна отдельная модель, где все поля опциональны.

class ProductUpdate(BaseModel):
    name: str | None = Field(default=None, min_length=3, max_length=80)
    category: str | None = Field(default=None, min_length=2, max_length=40)
    price: float | None = Field(default=None, gt=0)
    description: str | None = None
    is_available: bool | None = None

Ключевой прием — model_dump(exclude_unset=True). Он берет только поля, которые клиент реально передал в JSON.

@app.patch("/products/{product_id}", response_model=ProductRead, tags=["products"])
def update_product(
    product_id: Annotated[int, Path(ge=1, description="ID товара")],
    product_data: ProductUpdate,
):
    product = products_db.get(product_id)
    if product is None:
        raise HTTPException(
            status_code=status.HTTP_404_NOT_FOUND,
            detail="Товар не найден",
        )

    update_data = product_data.model_dump(exclude_unset=True)
    updated_product = product.model_copy(update=update_data)
    products_db[product_id] = updated_product

    return updated_product

Без exclude_unset=True есть риск перезаписать существующие значения на None, даже если клиент вообще не хотел менять эти поля.

DELETE: удаление

DELETE /products/{product_id} удаляет конкретный ресурс. Для успешного удаления часто используют 204 No Content.

@app.delete(
    "/products/{product_id}",
    status_code=status.HTTP_204_NO_CONTENT,
    tags=["products"],
)
def delete_product(
    product_id: Annotated[int, Path(ge=1, description="ID товара")]
):
    if product_id not in products_db:
        raise HTTPException(
            status_code=status.HTTP_404_NOT_FOUND,
            detail="Товар не найден",
        )

    del products_db[product_id]
    return None

Если хочется вернуть JSON с удаленным товаром, лучше использовать 200 OK, а не 204.

Ошибки как часть API-контракта

Ошибки должны быть предсказуемыми. Клиенту важно понимать, что произошло: ресурс не найден, данные не прошли валидацию или действие конфликтует с текущим состоянием.

def ensure_unique_product_name(name: str, excluded_id: int | None = None):
    for product_id, product in products_db.items():
        if excluded_id is not None and product_id == excluded_id:
            continue
        if product.name.lower() == name.lower():
            raise HTTPException(
                status_code=status.HTTP_409_CONFLICT,
                detail="Товар с таким именем уже существует",
            )

Для ошибок валидации тела запроса FastAPI сам вернет 422. Например, если price меньше или равен нулю, дополнительный if в эндпоинте не нужен.

def или async def

В FastAPI можно писать и обычные, и асинхронные path operation functions. Выбор зависит от того, что происходит внутри функции.

Event loop — это цикл событий, который управляет выполнением асинхронных задач. Когда корутина доходит до await, она добровольно приостанавливается и отдает управление event loop. В это время сервер может продолжить обработку других запросов, а затем вернуться к первой корутине, когда ожидаемая операция завершится.

Это полезно для операций ожидания: запрос к БД через async-драйвер, HTTP-запрос через httpx.AsyncClient, обращение к Redis, брокеру сообщений или файловому/сетевому API с async-интерфейсом. Но если внутри async def вызвать блокирующую функцию, event loop не сможет переключиться на другие задачи.

Шаг Что происходит Кто работает
1 Запрос A попадает в async def-эндпоинт FastAPI запускает корутину
2 Корутина доходит до await db_call() Ожидание уходит во внешний ресурс
3 Пока запрос A ждет, event loop может принять запрос B Сервер не простаивает
4 Внешний ресурс возвращает результат для запроса A Event loop продолжает первую корутину
Внутри эндпоинта Что выбрать Почему
нет await, обычная синхронная логика def проще; FastAPI выполнит функцию вне event loop
есть async-клиент БД, Redis, HTTPX, aio-pika async def можно использовать await и не блокировать event loop
CPU-heavy вычисления не держать в эндпоинте лучше вынести в отдельный процесс, очередь или executor

Наша in-memory логика синхронная и быстрая, поэтому в примерах достаточно def. Когда появятся асинхронные драйверы БД и внешние API, будем использовать async def.

Цикл событий и asyncio.gather

await позволяет не блокировать event loop, пока одна операция ждет внешний ресурс. Если внутри одного запроса нужно дождаться нескольких независимых async-операций, их можно запустить вместе через asyncio.gather.

import asyncio


async def load_price(product_id: int) -> float:
    await asyncio.sleep(1)
    return 99.0


async def load_stock(product_id: int) -> int:
    await asyncio.sleep(1)
    return 12


@app.get("/products/{product_id}/summary")
async def get_product_summary(product_id: int):
    price, stock = await asyncio.gather(
        load_price(product_id),
        load_stock(product_id),
    )

    return {"product_id": product_id, "price": price, "stock": stock}

Если ждать эти операции по очереди, запрос будет ждать примерно две секунды. С gather обе операции начинают ожидание сразу, поэтому итоговое время ближе к одной секунде.

Важно Что это значит
gather не делает CPU-код параллельным Он полезен для независимых операций ожидания: БД, HTTP, Redis, брокеры
Результаты возвращаются по порядку аргументов Первый результат соответствует первому awaitable, второй — второму
Блокирующий код все равно блокирует requests.get() или time.sleep() внутри async def не становятся async из-за gather

Блокирующий код внутри async def

Главная ошибка: написать async def, а внутри вызвать блокирующую операцию. Такой код блокирует event loop и мешает другим запросам.

Плохо:

import time


@app.get("/slow")
async def slow_endpoint():
    time.sleep(3)  # блокирует event loop
    return {"status": "done"}

Лучше для демонстрации ожидания:

import asyncio


@app.get("/slow")
async def slow_endpoint():
    await asyncio.sleep(3)
    return {"status": "done"}

В реальном коде вместо asyncio.sleep обычно будет await к асинхронному клиенту БД, Redis, HTTP-клиенту или брокеру сообщений.

Практика

  1. Добавьте PUT /products/{product_id} для полной замены товара.
  2. Добавьте ProductUpdate и PATCH /products/{product_id}.
  3. Добавьте DELETE /products/{product_id} со статусом 204.
  4. Добавьте проверку уникальности имени товара и возвращайте 409 при конфликте.

Если остается время: проверьте разницу между PUT и PATCH на поле description. При PUT отсутствующее поле заменяется значением по умолчанию. При PATCH отсутствующее поле не трогается.

Итоги

На этой лекции мы научились:
