Лекция 6: Тестирование FastAPI-приложения с pytest

До сих пор мы проверяли API вручную через Swagger UI и curl. Теперь превратим ожидаемое поведение приложения в исполняемые тесты. Они будут запускать FastAPI прямо внутри процесса pytest — без отдельного Uvicorn и без настоящего сетевого порта.

В конце лекции у проекта появится компактный набор тестов, который ловит регрессии в HTTP-контракте и не зависит от порядка запуска.

Приложение уже умеет выполнять CRUD для товаров, валидировать данные, выдавать JWT, определять текущего пользователя и разрешать изменение товаров только администратору.

В тестовых примерах считаем, что учебные Argon2-хэши из lifespan соответствуют локальным данным admin / admin-pass и user / user-pass. Эти пароли существуют только в тестовом окружении.

Что именно проверяет тест API

Часть контракта Пример проверки
маршрут и HTTP-метод GET /api/v1/products существует
статус создание возвращает 201, отсутствие — 404
тело ответа JSON соответствует публичной схеме
заголовки ошибка аутентификации содержит WWW-Authenticate
побочный эффект созданный товар появляется в списке, удалённый исчезает
правила доступа пользователь получает 403, администратор — успех

Хороший тест проверяет наблюдаемое поведение. Внутреннее устройство можно менять, пока внешний контракт остаётся прежним.

Уровни тестирования

Уровень Что запускаем Что получаем
unit одну функцию или класс быстрый и точный тест бизнес-правила
integration несколько компонентов вместе проверку их реального взаимодействия
API / component FastAPI-приложение через ASGI проверку HTTP-контракта без внешней сети
end-to-end развёрнутую систему и внешние сервисы максимум реализма, но более медленный и хрупкий тест

В этой лекции основной слой — API-тесты. Они охватывают маршрутизацию, Pydantic, зависимости, обработчики ошибок и сериализацию одним запросом.

Устанавливаем тестовые зависимости

uv add --dev pytest httpx anyio pytest-cov
  • pytest находит тесты, выполняет фикстуры и показывает значения в упавших assert.
  • httpx предоставляет HTTP-клиент; на нём основан TestClient.
  • anyio запускает тесты, объявленные через async def.
  • pytest-cov измеряет покрытие кода выполненными тестами.

Зависимости находятся в dev-группе: production-приложению они для запуска не нужны.

Настраиваем pytest

pyproject.toml

[tool.pytest.ini_options]
testpaths = ["tests"]
python_files = ["test_*.py"]
addopts = "-ra"
  • testpaths ограничивает поиск каталогом tests.
  • python_files задаёт соглашение об именах файлов.
  • -ra добавляет краткую сводку для пропущенных и ожидаемо упавших тестов.

Запускать тесты будем из корня проекта:

uv run pytest

conftest.py содержит общие фикстуры. Pytest обнаруживает их автоматически — импортировать этот файл в тестовые модули не нужно.

Первый тест с TestClient

tests/test_products.py

from fastapi.testclient import TestClient

from app.main import app


def test_list_products():
    with TestClient(app) as client:
        response = client.get("/api/v1/products")

    assert response.status_code == 200
    assert response.json() == []

Тест — обычная функция с префиксом test_. Хотя FastAPI является ASGI-приложением, запрос через TestClient синхронный: здесь не нужны async def и await.

TestClient не поднимает сервер

pytest
  └── TestClient
      └── ASGI-вызов
          └── FastAPI
              ├── middleware
              ├── зависимости
              ├── endpoint
              └── сериализация ответа

Запрос проходит через настоящий стек приложения, но остаётся внутри процесса. Это быстрее и стабильнее, чем перед каждым тестом запускать Uvicorn на случайном порту.

Почему клиент используется как контекстный менеджер

with TestClient(app) as client:
    response = client.get("/api/v1/products")
Момент Что происходит
вход в with выполняется код lifespan до yield, создаются хранилища
внутри блока тест отправляет запросы готовому приложению
выход из with выполняется код после yield, ресурсы освобождаются

Для нашего приложения это обязательно: ProductStorage и UserStorage создаются в lifespan.

Arrange — Act — Assert

def test_unknown_product_returns_404(client):
    # Arrange
    product_id = 999

    # Act
    response = client.get(f"/api/v1/products/{product_id}")

    # Assert
    assert response.status_code == 404
    assert response.json() == {"detail": "Товар не найден"}

Три фазы делают сценарий читаемым: подготовить данные, выполнить действие, проверить результат. Комментарии можно опустить, если границы и так очевидны.

Фикстура приложения

tests/conftest.py

import pytest
from fastapi import FastAPI

from app.core.config import Settings
from app.dependencies import get_settings
from app.main import create_app


@pytest.fixture
def app() -> FastAPI:
    settings = Settings(
        app_name="Products API Test",
        debug=False,
        api_prefix="/api/v1",
        jwt_secret_key="test-secret-not-for-production",
        jwt_algorithm="HS256",
        access_token_expire_minutes=5,
    )
    application = create_app(settings)
    application.dependency_overrides[get_settings] = lambda: settings
    return application

create_app(settings) задаёт конфигурацию при сборке приложения, а override гарантирует, что endpoints получат тот же объект через SettingsDep. Секрет предсказуем только в тестах: production-секрет нельзя копировать в тестовый код, логи или CI-переменные без необходимости.

Фикстура клиента и гарантированный teardown

tests/conftest.py

from collections.abc import Iterator

from fastapi.testclient import TestClient


@pytest.fixture
def client(app: FastAPI) -> Iterator[TestClient]:
    with TestClient(app) as test_client:
        yield test_client

Код до yield — setup, после него — teardown. Даже если тест упадёт, pytest выйдет из with и корректно завершит lifespan.

По умолчанию scope фикстуры — function: новый app и новый client создаются для каждого теста.

Изоляция важнее случайного порядка

Хрупкий тест Изолированный тест
ожидает товар, созданный другим тестом сам создаёт нужные данные
зависит от номера запуска проходит отдельно и в любом порядке
использует глобальный изменяемый storage получает свежий экземпляр приложения

Практическая проверка: любой тест должен проходить сам по себе через uv run pytest tests/test_products.py::test_name.

Подменяем зависимость, а не весь FastAPI

Для CRUD-тестов нам не обязательно каждый раз проверять криптографию и endpoint входа. Мы можем заменить зависимость, которая возвращает активного пользователя:

tests/conftest.py

from app.dependencies import get_current_active_user
from app.schemas import UserRead


def override_admin_user() -> UserRead:
    return UserRead(
        id=100,
        username="test-admin",
        role="admin",
        disabled=False,
    )


@pytest.fixture
def admin_client(app: FastAPI) -> Iterator[TestClient]:
    app.dependency_overrides[get_current_active_user] = (
        override_admin_user
    )

    try:
        with TestClient(app) as test_client:
            yield test_client
    finally:
        app.dependency_overrides.clear()

Ключ в dependency_overrides — исходная вызываемая функция зависимости, значение — её тестовая замена. FastAPI использует override даже для вложенной зависимости внутри проверки роли.

Когда override уместен

Подменяем Зачем
текущего пользователя проверить бизнес-правило отдельно от JWT
внешний HTTP-клиент не вызывать реальный платный или нестабильный сервис
репозиторий вернуть контролируемые данные или ошибку
часы детерминированно проверить срок действия

Override не заменяет интеграционные тесты. Для JWT нужны отдельные сценарии, которые проходят через настоящую выдачу и проверку токена.

Тестируем создание товара

tests/test_products.py

def test_create_product(admin_client):
    response = admin_client.post(
        "/api/v1/products",
        json={
            "name": "Mechanical Keyboard",
            "category": "electronics",
            "price": 129.90,
        },
    )

    assert response.status_code == 201
    body = response.json()
    assert body["id"] == 1
    assert body["name"] == "Mechanical Keyboard"
    assert body["category"] == "electronics"
    assert body["price"] == 129.90

Параметр json сериализует словарь и добавляет Content-Type: application/json. Pydantic-модель напрямую передавать не нужно.

Проверяем не только ответ, но и состояние

def test_created_product_appears_in_list(admin_client):
    create_response = admin_client.post(
        "/api/v1/products",
        json={
            "name": "Gaming Mouse",
            "category": "electronics",
            "price": 49.90,
        },
    )
    product = create_response.json()

    list_response = admin_client.get("/api/v1/products")

    assert list_response.status_code == 200
    assert list_response.json() == [product]

Первый assert подтверждает команду создания, второй запрос — наблюдаемый побочный эффект. Так тест ловит ситуацию, когда API вернул объект, но не сохранил его.

Полный CRUD-сценарий

def test_product_lifecycle(admin_client):
    created = admin_client.post(
        "/api/v1/products",
        json={
            "name": "Gaming Mouse",
            "category": "electronics",
            "price": 49.90,
        },
    )
    product_id = created.json()["id"]

    read = admin_client.get(f"/api/v1/products/{product_id}")
    assert read.status_code == 200

    updated = admin_client.patch(
        f"/api/v1/products/{product_id}",
        json={"is_available": False},
    )
    assert updated.status_code == 200
    assert updated.json()["is_available"] is False

    deleted = admin_client.delete(
        f"/api/v1/products/{product_id}"
    )
    assert deleted.status_code == 204
    assert deleted.content == b""

    missing = admin_client.get(f"/api/v1/products/{product_id}")
    assert missing.status_code == 404

Длинный workflow-тест полезен как один сквозной сценарий. Но точные правила валидации и отдельные ошибки лучше проверять короткими тестами — тогда причина падения видна сразу.

Тестируем ошибку валидации

def test_create_product_rejects_negative_price(admin_client):
    response = admin_client.post(
        "/api/v1/products",
        json={
            "name": "Gaming Mouse",
            "category": "electronics",
            "price": -1,
        },
    )

    assert response.status_code == 422
    errors = response.json()["detail"]
    assert any(error["loc"][-1] == "price" for error in errors)

Не стоит копировать весь текст ошибки Pydantic: он может стать подробнее без изменения контракта. Здесь важны статус и привязка ошибки к полю price.

Параметризация граничных случаев

import pytest


@pytest.mark.parametrize(
    ("payload", "field"),
    [
        ({"name": "", "category": "electronics", "price": 10}, "name"),
        ({"name": "Gaming Mouse", "price": 10}, "category"),
        ({"name": "Gaming Mouse", "category": "electronics", "price": 0}, "price"),
    ],
    ids=["empty-name", "missing-category", "zero-price"],
)
def test_invalid_product_payload(admin_client, payload, field):
    response = admin_client.post("/api/v1/products", json=payload)

    assert response.status_code == 422
    locations = [error["loc"][-1] for error in response.json()["detail"]]
    assert field in locations

Pytest создаст три самостоятельных тестовых случая. При падении имя вроде missing-category сразу укажет на проблемный набор данных.

Вход — это form data, не JSON

tests/test_auth.py

def test_login_returns_bearer_token(client):
    response = client.post(
        "/api/v1/auth/token",
        data={"username": "admin", "password": "admin-pass"},
    )

    assert response.status_code == 200
    body = response.json()
    assert body["token_type"] == "bearer"
    assert isinstance(body["access_token"], str)
    assert body["access_token"]

OAuth2PasswordRequestForm ожидает application/x-www-form-urlencoded, поэтому используется параметр data. Передача через json должна приводить к ошибке валидации.

Фикстура заголовка авторизации

tests/conftest.py

@pytest.fixture
def admin_headers(client: TestClient) -> dict[str, str]:
    response = client.post(
        "/api/v1/auth/token",
        data={"username": "admin", "password": "admin-pass"},
    )
    assert response.status_code == 200

    token = response.json()["access_token"]
    return {"Authorization": f"Bearer {token}"}

Эта фикстура проходит через настоящие проверку пароля и выпуск JWT. Она подходит для интеграционных auth-сценариев; для узких CRUD-тестов быстрее и яснее dependency_overrides.

Тестируем защищённый endpoint

def test_read_current_user(client, admin_headers):
    response = client.get(
        "/api/v1/auth/me",
        headers=admin_headers,
    )

    assert response.status_code == 200
    assert response.json() == {
        "id": 1,
        "username": "admin",
        "role": "admin",
        "disabled": False,

В одном сценарии проверяются выдача токена, схема Bearer, подпись JWT, загрузка пользователя и публичная схема ответа.

Неверные учётные данные

@pytest.mark.parametrize(
    ("username", "password"),
    [
        ("missing-user", "any-password"),
        ("admin", "wrong-password"),
    ],
)
def test_login_rejects_invalid_credentials(
    client, username, password
):
    response = client.post(
        "/api/v1/auth/token",
        data={"username": username, "password": password},
    )

    assert response.status_code == 401
    assert response.json() == {
        "detail": "Не удалось проверить учётные данные"
    }
    assert response.headers["www-authenticate"] == "Bearer"

Неизвестный username и неверный пароль дают одинаковый публичный ответ. Тест фиксирует это security-свойство, а не только статус.

Отсутствующий и повреждённый токен

def test_me_requires_token(client):
    response = client.get("/api/v1/auth/me")

    assert response.status_code == 401
    assert response.headers["www-authenticate"] == "Bearer"


def test_me_rejects_malformed_token(client):
    response = client.get(
        "/api/v1/auth/me",
        headers={"Authorization": "Bearer not-a-jwt"},
    )

    assert response.status_code == 401
    assert response.json() == {
        "detail": "Не удалось проверить учётные данные"
    }

Это разные ветви: в первом случае токен не извлечён, во втором — извлечён, но не прошёл декодирование.

401 и 403 — разные контракты

Ситуация Ожидаемый статус
токена нет, он повреждён или истёк 401 Unauthorized
пользователь распознан, но заблокирован 403 Forbidden
пользователь распознан, но роль не подходит 403 Forbidden

Статусы стоит проверять отдельно: ошибка в графе зависимостей легко превращает корректный 403 в вводящий клиента в заблуждение 401.

Тестируем роль настоящим токеном

def test_regular_user_cannot_create_product(client):
    login = client.post(
        "/api/v1/auth/token",
        data={"username": "user", "password": "user-pass"},
    )
    token = login.json()["access_token"]

    response = client.post(
        "/api/v1/products",
        headers={"Authorization": f"Bearer {token}"},
        json={
            "name": "Gaming Mouse",
            "category": "electronics",
            "price": 49.90,
        },
    )

    assert response.status_code == 403
    assert response.json() == {"detail": "Недостаточно прав"}

Этот тест не подменяет пользователя: он проверяет полный путь от формы входа до require_role("admin").

Unit-тест хранилища

tests/test_storage.py

Здесь HTTP-слой не нужен. Если сломалось правило идентификаторов, короткий unit-тест укажет на ProductStorage, а не на весь API.

Когда нужен асинхронный тест

TestClient — лучший старт для обычных API-тестов. Асинхронный тест нужен, когда внутри сценария требуется await: например, напрямую проверить данные через асинхронную сессию базы.

uv add --dev asgi-lifespan

import pytest
from asgi_lifespan import LifespanManager
from httpx import ASGITransport, AsyncClient


@pytest.mark.anyio
async def test_list_products_async(app):
    async with LifespanManager(app) as manager:
        transport = ASGITransport(app=manager.app)
        async with AsyncClient(
            transport=transport,
            base_url="http://test",
        ) as client:
            response = await client.get("/api/v1/products")

    assert response.status_code == 200

ASGITransport сам не запускает lifespan, поэтому он обёрнут в LifespanManager. Делать все тесты асинхронными «на всякий случай» не нужно.

Как тестировать ответ 500

По умолчанию TestClient пробрасывает необработанное исключение в тест. Это удобно: pytest показывает исходный traceback. Если нужно проверить собственное тело ответа 500, отключите это поведение:

with TestClient(
    app,
    raise_server_exceptions=False,
) as client:
    response = client.get("/endpoint-that-fails")

assert response.status_code == 500

Не используйте этот флаг глобально без причины: иначе полезный traceback превратится в менее информативный HTTP-ответ.

Запуск выбранных тестов

# весь набор
uv run pytest

# один файл
uv run pytest tests/test_auth.py

# один тест
uv run pytest tests/test_auth.py::test_me_requires_token

# тесты, в имени которых есть login
uv run pytest -k login

# подробные имена случаев
uv run pytest -v

Точечный запуск ускоряет локальный цикл, но перед завершением задачи нужно прогнать весь набор.

Покрытие кода

uv run pytest \
  --cov=app \
  --cov-branch \
  --cov-report=term-missing
  • --cov=app измеряет код приложения.
  • --cov-branch учитывает не только строки, но и ветви условий.
  • term-missing показывает номера непройденных строк.

Высокое покрытие показывает, что код выполнялся, но не доказывает качество проверок. Один тест без содержательных assert может покрыть много строк и почти ничего не гарантировать.

Что делает тест устойчивым

Практика Причина
один главный сценарий на тест из имени и падения понятно, что сломано
свежие данные для каждого теста нет зависимости от порядка
явные тестовые настройки результат не зависит от машины разработчика
проверка публичного контракта рефакторинг реализации не ломает тесты без причины
минимальная разумная подмена сохраняется ценность интеграции компонентов
никакой реальной сети набор быстрый и детерминированный

Типичные ошибки

Ошибка Как исправить
TestClient(app) создан вне with контекстный менеджер запускает lifespan
логин отправлен через json= для OAuth2-формы использовать data=
override остался после теста очищать dependency_overrides в finally
тесты используют один изменяемый storage создавать новое приложение на каждый тест
проверяется только статус 200 проверять JSON, заголовки и побочный эффект
точное сравнение нестабильного текста Pydantic проверять статус и расположение ошибочного поля

Практика

Задача: покрыть тестами Products API и аутентификацию, созданные в предыдущих лекциях.

  1. Добавьте dev-зависимости pytest, httpx, anyio и pytest-cov.
  2. Создайте каталог tests и настройте его в pyproject.toml.
  3. Добавьте фикстуры нового приложения и TestClient с запуском lifespan.
  4. Проверьте пустой список, создание, чтение, частичное обновление и удаление товара.
  5. Параметризуйте ошибки валидации полей товара.
  6. Через dependency_overrides изолируйте CRUD-тесты от механизма JWT.
  7. Отдельно проверьте успешный вход, неверный пароль, неизвестного пользователя, отсутствующий и повреждённый токен.
  8. Проверьте 403 для обычного пользователя и успешное изменение товара администратором.
  9. Запустите весь набор и отчёт ветвления через --cov-branch.

Дополнительная задача: сделайте функцию создания access token управляемой временем и добавьте детерминированный тест истёкшего JWT без sleep.

Итоги

На этой лекции мы научились:

  • различать unit-, integration-, API- и end-to-end-тесты.
  • запускать FastAPI через TestClient без отдельного сервера.
  • гарантированно выполнять lifespan через контекстный менеджер.
  • создавать изолированные фикстуры приложения и клиента.
  • подменять зависимости через app.dependency_overrides.
  • проверять CRUD, валидацию, заголовки и побочные эффекты.
  • тестировать полный JWT-поток и различать 401 и 403.
  • параметризовать граничные случаи и измерять покрытие ветвей.
  • понимать, когда нужен AsyncClient.

На следующей лекции заменим in-memory-хранилище настоящей реляционной базой данных и начнём работать с моделями и CRUD через SQLAlchemy.
