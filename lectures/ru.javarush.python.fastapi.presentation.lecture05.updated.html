Лекция 5: Аутентификация, OAuth2 и JWT в FastAPI

Добавим в учебное приложение пользователей, безопасную проверку паролей, выдачу JWT access token и зависимости, которые определяют текущего пользователя и его права.

База данных пока остаётся in-memory. Это позволяет сосредоточиться на потоке аутентификации; позже хранилище пользователей заменится SQLAlchemy без переписывания HTTP-контракта.

Аутентификация и авторизация

Понятие Вопрос Пример
Аутентификация кто выполняет запрос? проверить логин/пароль или access token
Авторизация что этому пользователю разрешено? только администратор может удалить товар

Сначала система устанавливает личность пользователя, затем проверяет его состояние, роль или конкретные разрешения.

401 Unauthorized означает, что личность не установлена или токен недействителен. 403 Forbidden — личность установлена, но действие запрещено.

Поток входа по паролю

  1. Клиент отправляет username и password на POST /api/v1/auth/token.
  2. API находит пользователя и сравнивает пароль с сохранённым хэшем.
  3. При успехе API подписывает короткоживущий access token.
  4. Клиент передаёт токен в заголовке Authorization: Bearer ....
  5. Защищённый эндпоинт проверяет подпись, срок действия и пользователя.
  6. Затем выполняется авторизация: проверка активности, роли или разрешения.

Пароль передаётся только при входе. После этого клиент предъявляет access token.

OAuth2, Bearer и JWT — разные вещи

Термин Что означает
OAuth2 фреймворк авторизации: описывает способы получения и применения access token
Bearer token токен предъявителя: доступ получает тот, кто может его предъявить
JWT формат подписанного токена; OAuth2 не требует, чтобы токен был JWT

Используем password flow для учебного first-party приложения. Для входа через Google или другого внешнего провайдера обычно применяют Authorization Code с PKCE и OpenID Connect, а не собственную форму пароля.

Access token и refresh token

Access token

Refresh token

Токен Назначение Обычно
Access token доступ к защищённым эндпоинтам короткий срок жизни, передаётся часто
Refresh token получение новой пары токенов без повторного ввода пароля долгий срок, передаётся только auth-сервису

Refresh token требует отдельной политики хранения, ротации, отзыва и обнаружения повторного использования. На этой лекции реализуем access token; refresh flow вернётся в углублённой лекции по безопасности.

Что такое JWT

JWT — компактный формат передачи JSON-утверждений. Токен состоит из трёх частей:

base64url(header).base64url(payload).signature
graph TD A["JWT token"] --> B["Header"] A --> C["Payload"] A --> D["Signature"] B -- "содержит" --> B1["alg: HS256"] B -- "содержит" --> B2["typ: JWT"] C -- "содержит" --> C1["sub: 42"] C -- "содержит" --> C2["exp: 1782048000"] C -- "содержит" --> C3["type: access"] D -- "создаётся из" --> H["Header + '.' + Payload"] D -- "подписывается" --> S["Секретный ключ"] style D fill:#cfc,stroke:#333
Часть Содержимое
Header тип токена и алгоритм подписи, например HS256
Payload claims: sub, exp и другие данные
Signature защищает header и payload от незаметного изменения

JWT обычно не зашифрован. Payload может прочитать любой получатель токена, поэтому пароли, секреты и чувствительные данные туда не помещают.

Claims, которые используем

{
  "sub": "42",
  "exp": 1782048000,
  "iat": 1782046200,
  "type": "access"
}
  • sub — строковый идентификатор пользователя.
  • exp — момент окончания действия токена.
  • iat — момент выпуска токена.
  • type — защита от использования другого вида токена как access token.

Роль намеренно не кладём в токен: зависимость загрузит актуального пользователя из хранилища, поэтому блокировка и изменение роли применятся сразу.

Секрет JWT

Сгенерировать случайный секрет можно командой:

uv run python -c "import secrets; print(secrets.token_hex(32))"

.env

JWT_SECRET_KEY=replace-with-generated-value
JWT_ALGORITHM=HS256
ACCESS_TOKEN_EXPIRE_MINUTES=30

Секрет не коммитится в Git и не записывается прямо в security.py. При утечке его нужно заменить; старые токены после замены перестанут проходить проверку.

Настройки JWT

app/core/config.py

from pydantic import SecretStr
from pydantic_settings import BaseSettings


class Settings(BaseSettings):
    jwt_secret_key: SecretStr
    jwt_algorithm: str = "HS256"
    access_token_expire_minutes: int = 30

SecretStr маскирует значение при обычном выводе модели. Для передачи ключа в PyJWT явно вызывается get_secret_value().

Схемы пользователя

from typing import Literal

from pydantic import BaseModel, Field


Role = Literal["user", "admin"]


class UserRead(BaseModel):
    id: int
    username: str
    role: Role = "user"
    disabled: bool = False


class UserInDB(UserRead):
    hashed_password: str

hashed_password существует только во внутренней схеме и не попадёт в ответы API.

Схемы токена

class Token(BaseModel):
    access_token: str
    token_type: Literal["bearer"] = "bearer"


class TokenPayload(BaseModel):
    sub: str
    exp: int
    iat: int
    type: Literal["access"]

Token — публичный ответ клиенту. TokenPayload — проверенная внутренняя форма claims после декодирования JWT.

Пароль нельзя хранить как текст

Подход Свойство
Шифрование данные можно расшифровать ключом — для паролей это не нужно
Криптографический хэш пароля односторонняя и намеренно дорогая проверка

Argon2 сохраняет параметры алгоритма и случайную соль внутри строки хэша. Одинаковые пароли обычно получают разные хэши, но оба успешно проверяются.

Хэш защищает пароли при утечке базы, но слабый пароль всё равно можно подобрать. Поэтому нужны ограничения на пароль и защита endpoint входа от перебора.

Хэширование и проверка

app/security.py

from pwdlib import PasswordHash


password_hash = PasswordHash.recommended()
DUMMY_HASH = password_hash.hash("not-a-real-password")


def hash_password(password: str) -> str:
    return password_hash.hash(password)


def verify_password(password: str, hash_: str) -> bool:
    return password_hash.verify(password, hash_)

DUMMY_HASH нужен, чтобы при неизвестном username всё равно выполнить дорогую проверку и уменьшить различие во времени ответа.

Хранилище пользователей

app/storage.py

class UserStorage:
    def __init__(self) -> None:
        self.users: dict[int, UserInDB] = {}

    def add(self, user: UserInDB) -> None:
        self.users[user.id] = user

    def get(self, user_id: int) -> UserInDB | None:
        return self.users.get(user_id)

    def get_by_username(self, username: str) -> UserInDB | None:
        for user in self.users.values():
            if user.username == username:
                return user
        return None

Lifespan создаёт одно UserStorage и добавляет учебного пользователя с заранее сгенерированным Argon2-хэшем. В реальном приложении это будет запрос к базе данных.

Добавляем учебных пользователей в lifespan

app/lifespan.py

async def lifespan(app: FastAPI):
    users = UserStorage()
    users.add(
        UserInDB(
            id=1,
            username="admin",
            role="admin",
            hashed_password="$argon2id$...",
        )
    )
    app.state.user_storage = users

    yield

Argon2-хэш один раз генерируется локально и вставляется вместо $argon2id$.... Открытый пароль в приложении не хранится. Декоратор @asynccontextmanager и очистка после yield остаются такими же, как в лекции 4.

Проверяем логин и пароль

def authenticate_user(
    storage: UserStorage,
    username: str,
    password: str,
) -> UserInDB | None:
    user = storage.get_by_username(username)

    if user is None:
        verify_password(password, DUMMY_HASH)
        return None

    if not verify_password(password, user.hashed_password):
        return None

    return user

Клиенту возвращается одинаковая ошибка и для неизвестного username, и для неверного пароля. Это не раскрывает, существует ли такой пользователь.

Создаём access token

app/security.py

def create_access_token(subject: str, settings: Settings) -> str:
    now = datetime.now(timezone.utc)
    expires_at = now + timedelta(minutes=30)
    payload = {
        "sub": subject,
        "iat": now,
        "exp": expires_at,
        "type": "access",
    }
    return jwt.encode(
        payload,
        settings.jwt_secret_key.get_secret_value(),
        algorithm=settings.jwt_algorithm,
    )

В полном коде число 30 берётся из settings.access_token_expire_minutes. В sub передаём строковый ID пользователя: str(user.id).

Проверяем и разбираем токен

def decode_access_token(token: str, settings: Settings):
    payload = jwt.decode(
        token,
        settings.jwt_secret_key.get_secret_value(),
        algorithms=[settings.jwt_algorithm],
        options={"require": ["sub", "exp", "iat"]},
    )
    token_data = TokenPayload.model_validate(payload)

    if token_data.type != "access":
        raise InvalidTokenError("Unexpected token type")

    return token_data

jwt.decode() проверяет подпись и стандартные временные claims. Затем Pydantic проверяет форму payload.

OAuth2PasswordBearer

from fastapi.security import OAuth2PasswordBearer


oauth2_scheme = OAuth2PasswordBearer(
    tokenUrl="api/v1/auth/token",
)

OAuth2PasswordBearer:

  • читает заголовок Authorization: Bearer <token>.
  • возвращает строку токена зависимости.
  • добавляет security scheme и кнопку Authorize в OpenAPI.

Он не проверяет подпись JWT и не загружает пользователя. Эту работу выполняют наши следующие зависимости. tokenUrl должен указывать на реальный endpoint выдачи токена.

OAuth2PasswordRequestForm

LoginForm = Annotated[
    OAuth2PasswordRequestForm,
    Depends(),
]
  • данные передаются как application/x-www-form-urlencoded, не JSON.
  • обязательные имена полей: username и password.
  • форма также поддерживает OAuth2-поля scope, client_id и client_secret.

python-multipart нужен FastAPI для разбора формы.

Общая ошибка аутентификации

def invalid_credentials() -> HTTPException:
    return HTTPException(
        status_code=status.HTTP_401_UNAUTHORIZED,
        detail="Не удалось проверить учётные данные",
        headers={"WWW-Authenticate": "Bearer"},
    )


TokenDep = Annotated[str, Depends(oauth2_scheme)]

Заголовок WWW-Authenticate: Bearer сообщает клиенту, какая схема аутентификации ожидается.

Endpoint входа

app/routers/auth.py

@router.post("/token", response_model=Token)
def login(
    form_data: LoginForm,
    users: UserStorageDep,
    settings: SettingsDep,
) -> Token:
    user = authenticate_user(
        users, form_data.username, form_data.password
    )
    if user is None:
        raise invalid_credentials()

    token = create_access_token(str(user.id), settings)
    return Token(access_token=token)

Одинаковый ответ используется для неизвестного username и неправильного пароля. Успешный ответ соответствует схеме Token.

Получаем текущего пользователя

app/dependencies.py

def get_current_user(
    token: TokenDep,
    users: UserStorageDep,
    settings: SettingsDep,
) -> UserRead:
    try:
        token_data = decode_access_token(token, settings)
        user = users.get(int(token_data.sub))
    except (InvalidTokenError, ValidationError, ValueError):
        raise invalid_credentials()

    if user is None:
        raise invalid_credentials()

    return UserRead.model_validate(user.model_dump())

Даже валидный токен не гарантирует, что пользователь всё ещё существует, поэтому зависимость проверяет хранилище.

Активный пользователь и статусы

def get_current_active_user(user: CurrentUserDep) -> UserRead:
    if user.disabled:
        raise HTTPException(
            status_code=status.HTTP_403_FORBIDDEN,
            detail="Пользователь заблокирован",
        )
    return user


ActiveUserDep = Annotated[
    UserRead, Depends(get_current_active_user)
]

CurrentUserDep — алиас зависимости get_current_user. Токен здесь уже валиден, но заблокированному пользователю запрещено выполнять операции, поэтому возвращается 403.

Endpoint /auth/me

@router.get("/me", response_model=UserRead)
def read_current_user(
    current_user: ActiveUserDep,
) -> UserRead:
    return current_user

Последовательность зависимостей:

read_current_user
└── get_current_active_user
    └── get_current_user
        ├── OAuth2PasswordBearer
        ├── UserStorageDep
        └── SettingsDep

В Swagger UI можно получить токен через кнопку Authorize и затем вызвать GET /api/v1/auth/me.

Проверка роли

def require_role(role: Role):
    def dependency(user: ActiveUserDep) -> UserRead:
        if user.role != role:
            raise HTTPException(
                status_code=status.HTTP_403_FORBIDDEN,
                detail="Недостаточно прав",
            )
        return user

    return dependency


AdminUserDep = Annotated[
    UserRead,
    Depends(require_role("admin")),
]

Если ролей и разрешений станет много, простое сравнение заменится системой permissions или OAuth2 scopes.

Что происходит при защищённом запросе

Шаг Действие
1 OAuth2PasswordBearer извлекает Bearer token
2 decode_access_token проверяет подпись, срок и claims
3 get_current_user загружает актуального пользователя
4 get_current_active_user проверяет блокировку
5 require_role проверяет право на операцию
6 эндпоинт выполняется или возвращается 401/403

Минимальный security checklist

  • не хранить и не логировать пароли в открытом виде.
  • использовать адаптивный password hash: Argon2, bcrypt или scrypt.
  • хранить JWT secret вне репозитория и регулярно управлять секретами.
  • фиксировать допустимый алгоритм на сервере.
  • не помещать секретные данные в JWT payload.
  • задавать короткий срок действия access token.
  • передавать пароль и токены только через HTTPS.
  • возвращать общую ошибку входа и ограничивать частоту попыток.
  • не считать logout решённым только потому, что клиент удалил JWT.

Учебная in-memory-реализация не решает отзыв access token, refresh rotation, MFA, аудит, rate limiting и управление сессиями.

Практика

Задача: добавить access-token аутентификацию и разграничить доступ к Products API.

  1. Установите pyjwt, pwdlib[argon2] и python-multipart через uv.
  2. Добавьте JWT-настройки в Settings и сгенерируйте секрет для локального .env.
  3. Создайте схемы UserRead, UserInDB, Token и TokenPayload.
  4. Добавьте UserStorage и двух учебных пользователей: user и admin с Argon2-хэшами.
  5. Реализуйте authenticate_user, создание и декодирование access token.
  6. Создайте POST /api/v1/auth/token и GET /api/v1/auth/me.
  7. Добавьте зависимости CurrentUserDep, ActiveUserDep и AdminUserDep.
  8. Оставьте чтение товаров публичным, а изменение разрешите только администратору.
  9. Проверьте: успешный вход, неверный пароль, отсутствующий токен, испорченный токен, истёкший токен и ответ 403 для обычного пользователя.

Дополнительная задача: добавьте endpoint, который блокирует пользователя, и проверьте, что уже выданный JWT перестаёт давать доступ из-за повторной загрузки пользователя.
