Уровень 15: надёжность Celery — retry, acknowledgements и DLQ

На прошлом уровне мы развели задачи по очередям reports и maintenance. Теперь разберём, что происходит, когда база временно недоступна, worker завершается посреди задачи или сообщение невозможно обработать.

После занятия вы сможете отличить Celery retry от повторной доставки RabbitMQ, безопасно включить позднее подтверждение для задачи, которую не страшно запустить повторно, и объяснить, при каких условиях сообщение действительно попадает в DLQ.

Маршрутизация решает, где выполнить задачу. Надёжность отвечает на другой вопрос: что делать после сбоя.

Почему обработка ошибок в асинхронных системах критически важна?

Обычный HTTP-запрос завершается на глазах у пользователя: API сразу возвращает успех или ошибку. Фоновая задача выполняется позже, поэтому API уже мог ответить 202 Accepted, хотя сама работа ещё не началась.

sequenceDiagram participant U as Пользователь participant API as FastAPI participant B as RabbitMQ participant W as Celery worker U->>API: создать отчёт API->>B: поставить задачу API-->>U: 202 Accepted + task_id B-->>W: доставить задачу W->>W: ошибка во время выполнения Note over U,W: HTTP-ответ уже отправлен — сбой нужно обнаружить отдельно
  • Ошибка не видна сразу: пользователь получил task_id, но результат может так и не появиться.
  • Операция может выполниться частично: одна запись сохранена, а следующая внешняя операция не состоялась.
  • Бесконтрольный retry усиливает сбой: сотни задач одновременно атакуют недоступную базу или API.
  • Потеря процесса создаёт дубликаты: broker может передать неподтверждённое сообщение повторно.
  • Без наблюдаемости трудно найти причину: нужны task_id, состояние задачи, логи и метрики очереди.

Надёжная система не обещает, что ошибок не будет. Она делает сбой видимым, ограничивает его последствия и предоставляет безопасный путь восстановления.

Основные подходы к обработке ошибок

  • Retry: повторяет задачу после ожидаемой временной ошибки.
  • Timeout: ограничивает зависшую I/O-операцию или задачу.
  • Acknowledgement: сообщает broker, что делать с доставленным сообщением.
  • DLQ: изолирует отклонённые сообщения для анализа и контролируемого replay.
  • Логи и мониторинг: позволяют восстановить последовательность событий.

Это не последовательные стадии одного алгоритма, а независимые механизмы. Дальше разберём, какой сбой решает каждый из них.

Сначала классифицируем ошибку

СитуацияПримерПравильная реакция
Временная ошибкаобрыв соединения, timeout, HTTP 503retry с задержкой
Постоянная ошибканевалидные данные, HTTP 400/401/404завершить без retry, исследовать причину
Потеря процессаконтейнер остановлен, OOM, hard time limitredelivery неподтверждённого сообщения
Poison messageсообщение стабильно ломает обработчикизолировать в DLQ

Retry каждой ошибки подряд не делает систему надёжнее. Постоянная ошибка лишь повторится несколько раз и создаст лишнюю нагрузку.

Гарантия — не «ровно один раз»

ACK — подтверждение consumer для RabbitMQ: «сообщение обработано, его можно удалить из очереди». Момент отправки ACK определяет, что произойдёт при падении процесса.

РежимКогда отправляется ACKЕсли процесс исчез во время задачи
По умолчаниюдо выполнения задачисообщение уже подтверждено и не будет доставлено повторно
acks_late=Trueпосле выполнения задачинеподтверждённое сообщение может вернуться в очередь

Поздний ACK уменьшает риск потери задачи, но создаёт окно дублирования: бизнес-операция могла завершиться, а соединение оборвалось прямо перед ACK. RabbitMQ доставит сообщение снова, и код выполнится второй раз.

  • At-most-once: задача выполнится не более одного раза, но может потеряться.
  • At-least-once: с поздним ACK и корректной обработкой потери worker задача не должна потеряться при сбое, но может выполниться повторно.
  • Exactly-once: нельзя получить одной настройкой Celery или RabbitMQ. Бизнес-операция должна безопасно переносить повторный запуск.

Важное уточнение: acks_late означает «ACK после выполнения», а не обязательно «ACK только после успеха». По умолчанию Celery подтверждает и упавшую задачу через task_acks_on_failure_or_timeout=True; нужное поведение при ошибке и потере worker настраивается отдельно.

Поэтому сначала убеждаемся, что повторный запуск не испортит данные, а затем включаем позднее подтверждение.

Retry, redelivery и DLQ решают разные задачи

МеханизмКто запускаетЧто происходит
Celery retryкод задачипубликуется новое сообщение с тем же task_id
RabbitMQ redeliverybrokerповторно доставляется прежнее неподтверждённое сообщение
Dead letteringbrokerотклонённое или просроченное сообщение маршрутизируется через DLX

max_retries сам по себе не создаёт DLQ. Чтобы финальная ошибка попала туда, очередь должна иметь DLX, а сообщение должно быть отклонено без возврата в исходную очередь.

Retry нужен только для ожидаемых временных ошибок

class TemporaryReportError(Exception):
    """Сбой, после которого отчёт имеет смысл попробовать снова."""


@celery_app.task(
    bind=True,
    name="app.tasks.generate_product_report",
    autoretry_for=(TemporaryReportError,),
    retry_kwargs={"max_retries": 3},
    retry_backoff=2,
    retry_backoff_max=60,
    retry_jitter=True,
)
def generate_product_report(self, ...):
    ...
  • autoretry_for ограничивает список повторяемых ошибок.
  • max_retries=3 означает максимум три повтора после первого запуска.
  • retry_backoff=2 задаёт интервалы порядка 2, 4 и 8 секунд.
  • retry_jitter=True добавляет случайность, чтобы много задач не повторились одновременно.

Retry публикует новое сообщение

sequenceDiagram participant W as Celery worker participant B as RabbitMQ participant R as Redis backend W->>W: попытка 1 — временная ошибка W->>B: новое сообщение с тем же task_id W->>R: состояние RETRY B-->>W: попытка 2 после countdown W->>W: успешное выполнение W->>R: состояние SUCCESS

self.retry() не является nack исходного сообщения. Celery завершает текущую попытку специальным состоянием RETRY и отправляет следующую попытку в ту же очередь.

acks_late защищает от потери процесса

@celery_app.task(
    bind=True,
    name="app.tasks.generate_product_report",
    acks_late=True,
    reject_on_worker_lost=True,
    acks_on_failure_or_timeout=False,
    ...,
)
def generate_product_report(self, ...):
    ...
  • acks_late=True переносит ACK на момент после выполнения.
  • reject_on_worker_lost=True разрешает requeue при внезапной потере процесса.
  • acks_on_failure_or_timeout=False отклоняет финально упавшую задачу вместо обычного ACK.

Осторожно: потерянная задача может выполниться повторно, а постоянный аварийный сбой способен создать цикл. Эти настройки разумны только тогда, когда повторный запуск не портит данные, и вместе с DLQ/лимитом повторов.

graph TD A[Worker получил задачу] --> B{Что произошло?} B -->|Ожидаемая временная ошибка| C[Celery retry] C --> D[Новое сообщение
с countdown] B -->|Процесс исчез до ACK| E[RabbitMQ redelivery] E --> F[Прежнее сообщение

Retry контролируется приложением. Redelivery и dead lettering — реакция broker на статус подтверждения сообщения.

У задачи два уровня таймаутов

from celery.exceptions import SoftTimeLimitExceeded


@celery_app.task(
    soft_time_limit=25,
    time_limit=30,
    ...,
)
def generate_product_report(...):
    try:
        return build_report(...)
    except SoftTimeLimitExceeded:
        logger.warning("Report exceeded soft time limit")
        raise
  • Timeout клиента БД или HTTP ограничивает отдельную I/O-операцию.
  • Soft time limit даёт задаче шанс освободить ресурсы.
  • Hard time limit принудительно завершает исполняющий процесс.

Time limits зависят от worker pool и сигналов ОС. Для демонстрации используйте Docker worker с prefork; локальный --pool=solo на Windows для этой практики не подходит.

Как объявить DLQ

graph LR RQ((reports)) -->|reject / nack
requeue=false| DLX[dlx] DLX -->|failed| DLQ((dlq)) DLQ --> HUMAN[анализ причины] HUMAN -->|после исправления| REPLAY[контролируемый replay]

RabbitMQ отправляет сообщение в DLX, когда оно отклонено без requeue, истекло по TTL, вытеснено лимитом очереди или превысило delivery limit quorum-очереди.

В проекте топология описана объектами Kombu — отдельные RabbitMQ config/definitions-файлы не нужны. Используем общую очередь dlq: к тому же dlx позднее можно подключить другие рабочие очереди, а исходную очередь и причину dead lettering найти в заголовке x-death.

DEAD_LETTER_EXCHANGE = Exchange("dlx", type="direct", durable=True)
DEAD_LETTER_QUEUE = Queue(
    "dlq",
    exchange=DEAD_LETTER_EXCHANGE,
    routing_key="failed",
    durable=True,
)

REPORT_QUEUE = Queue(
    "reports",
    exchange=Exchange("reports", type="direct", durable=True),
    routing_key="reports",
    queue_arguments={
        "x-dead-letter-exchange": "dlx",
        "x-dead-letter-routing-key": "failed",
    },
)
MAINTENANCE_QUEUE = Queue(
    "maintenance",
    exchange=Exchange("maintenance", type="direct", durable=True),
    routing_key="maintenance",
)

task_queues = (REPORT_QUEUE, MAINTENANCE_QUEUE)

task_routes = {
    "app.tasks.generate_product_report": {
        "queue": "reports",
        "declare": (REPORT_QUEUE, DEAD_LETTER_QUEUE),
    },
}
task_default_queue = "maintenance"
  1. task_queues хранит рабочую очередь с DLX-аргументами;
  2. declare создаёт рабочую очередь, общую dlq и необходимые exchanges при отправке отчёта;
  3. dlq не добавляется в task_queues, поэтому worker не забирает сообщения из неё.

Аргументы очереди неизменяемы. Если reports уже была создана без DLX, перед первым запуском новой версии удалите пустую очередь reports в RabbitMQ Management — Celery создаст её заново.

Неизлечимую задачу отклоняем без requeue

from celery.exceptions import Reject


@celery_app.task(
    bind=True,
    acks_late=True,
    acks_on_failure_or_timeout=False,
)
def generate_product_report(
    self,
    simulate_permanent_error=False,
):
    if simulate_permanent_error:
        exc = PermanentReportError("Invalid report")
        logger.error(
            "Permanent report error",
            extra={"task_id": self.request.id},
        )
        raise Reject(exc, requeue=False)

Reject(..., requeue=False) — явный broker-level отказ. Если у исходной очереди настроен DLX, RabbitMQ направит сообщение в DLQ.

Повторно публиковать сообщения из DLQ следует только после исправления причины. Автоматический бесконечный replay возвращает poison message в рабочую очередь.

Следующий шаг — внешняя наблюдаемость: Sentry группирует исключения и отправляет уведомления, а ELK собирает логи разных API и workers в одном месте для поиска и анализа. Здесь мы только фиксируем их роль; полноценную интеграцию разберём на отдельном уровне про наблюдаемость.

Практика: временная ошибка, падение и DLQ

  1. Добавьте к отчёту bind=True, ограниченный retry с backoff/jitter и параметр simulate_failures.
  2. Включите для отчёта acks_late, reject_on_worker_lost и осознанное поведение при финальной ошибке.
  3. Объявите общие dlx, dlq и binding через Kombu; добавьте DLX-аргументы к рабочей очереди.
  4. Запустите инфраструктуру и workers: docker compose up -d --build --wait.
  5. Запустите API локально: uv run uvicorn app.main:app --reload.
  6. Отправьте отчёт с simulate_failures=2 и проследите RETRY → SUCCESS во Flower.
  7. Отправьте долгий отчёт, остановите celery-reports во время выполнения и после его запуска проверьте redelivery.
  8. Отправьте отчёт с simulate_permanent_error=true, убедитесь, что рабочая очередь продолжает обрабатываться, а сообщение появилось в общей очереди dlq.
  9. Добавьте тесты на параметры retry, маршрутизацию, безопасный повторный запуск отчёта и отсутствие retry для постоянной ошибки.

Что важно запомнить

  • Retry обрабатывает ожидаемую ошибку и публикует новую попытку.
  • Redelivery возвращает неподтверждённое сообщение после потери consumer.
  • DLQ требует DLX и конкретного условия dead-lettering.
  • acks_late означает возможность повторного выполнения, а не exactly-once.
  • Позднее подтверждение включают только тогда, когда повторный запуск задачи безопасен.
  • Backoff ограничиваем сверху и дополняем jitter.
  • Flower показывает задачи, RabbitMQ Management — состояние сообщений и очередей.
