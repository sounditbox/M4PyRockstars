Лекция 10: MongoDB для характеристик товаров

В Products API основные данные товара уже хранятся в PostgreSQL. Но характеристики клавиатуры, монитора и мебели выглядят по-разному и быстро расширяют единую Pydantic-схему.

Добавим MongoDB для необязательных расширенных характеристик существующего товара и реализуем endpoint /products/{product_id}/attributes через PyMongo Async.

Когда MongoDB действительно полезна

  • характеристики естественно читаются и изменяются как единый документ;
  • набор полей сильно зависит от категории товара;
  • новые характеристики появляются чаще, чем меняется основная модель Product;
  • по расширенным атрибутам нужны отдельные документные запросы.

Для небольшого фиксированного набора полей PostgreSQL JSON/JSONB обычно достаточно. MongoDB выбираем не ради скорости или масштаба сами по себе, а когда документ становится самостоятельной моделью.

SQL и NoSQL могут масштабироваться разными способами. Выбор хранилища начинается с модели данных и запросов, а не с лозунга «вертикально против горизонтально».

NoSQL — семейство моделей

Модель Пример Для каких задач
Document MongoDB вложенные объекты, каталоги, профили, контент
Key-value Redis кэш, сессии, счётчики, данные с TTL
Graph Neo4j маршруты, социальные связи, рекомендации
Wide-column Cassandra распределённая запись больших потоков данных

NoSQL — не одна технология и не «база без SQL». Это семейство моделей с разными способами хранения и запросов. В этой лекции нужна document model: один документ содержит расширенные характеристики одного товара.

MongoDB хранит документы в формате BSON: он похож на JSON, но поддерживает дополнительные типы, включая ObjectId, даты, бинарные данные и Decimal128.

SQL и документная модель

Реляционная модель Документная модель
таблицы, строки, колонки collections и BSON-документы
связи через ForeignKey и JOIN embedding или reference
схема меняется миграциями документы могут эволюционировать постепенно
primary key _id, обычно ObjectId

MongoDB не отменяет схему: вход API проверяет Pydantic, а база использует индексы и при необходимости validators. Правильнее говорить schema-flexible, а не schema-less.

Документ product_attributes

{
  "_id": {"$oid": "6697bbef47e2631f1492be5a"},
  "product_id": 42,
  "attributes": {
    "switch": "brown",
    "layout": "ANSI",
    "wireless": false,
    "connection": "USB-C"
  },
  "created_at": {"$date": "2026-07-21T12:00:00Z"},
  "updated_at": {"$date": "2026-07-21T12:00:00Z"}
}
  • product_id ссылается на товар в PostgreSQL на уровне приложения;
  • attributes содержит небольшие скалярные значения;
  • на один товар допускаем не более одного документа;
  • MongoDB не может создать настоящий ForeignKey к PostgreSQL.

Базовый CRUD в mongosh

db.product_attributes.insertOne({
  product_id: 42,
  attributes: {
    layout: "ANSI",
    wireless: false
  }
})

db.product_attributes.findOne({product_id: 42})

db.product_attributes.updateOne(
  {product_id: 42},
  {$set: {"attributes.wireless": true}}
)

db.product_attributes.deleteOne({product_id: 42})

После имени collection вызывается операция. У findOne и deleteOne объект задаёт фильтр. У updateOne первый объект выбирает документ, а второй описывает изменение.

Это команды интерактивной оболочки mongosh. Позже те же операции через PyMongo Async будем вызывать с await.

Фильтры, projection и операторы

db.product_attributes.find(
  {
    "attributes.refresh_rate": {$gte: 120},
    "attributes.color": {$in: ["black", "white"]}
  },
  {
    _id: 0,
    product_id: 1,
    "attributes.refresh_rate": 1
  }
).sort({"attributes.refresh_rate": -1}).limit(10)

db.product_attributes.updateOne(
  {product_id: 42},
  {$unset: {"attributes.connection": ""}}
)
  • $gte, $gt, $lte, $lt сравнивают значения;
  • $in проверяет вхождение в набор;
  • projection оставляет только нужные поля;
  • $set, $unset и $inc изменяют документ.

От SQL к синтаксису MongoDB

SQL MongoDB
SELECT * FROM product_attributes db.product_attributes.find({})
WHERE product_id = 42 {product_id: 42}
SELECT product_id {product_id: 1, _id: 0}
UPDATE ... SET updateOne(filter, {$set: changes})
DELETE ... WHERE deleteOne(filter)
CREATE UNIQUE INDEX createIndex(keys, {unique: true})

MongoDB-запрос состоит из обычных вложенных объектов. Но операции выполняются над документом целиком или его путями, а не над строками и колонками таблицы.

Reference между базами, embedding внутри документа

flowchart LR subgraph PG["PostgreSQL"] P["Product
id = 42"] -->|"category_id"| C["Category"] end subgraph MDB["MongoDB"] PA["ProductAttributes
product_id = 42"] --> A["attributes {...}"] end P -. "application-level reference" .-> PA

Между базами хранится обычный product_id. Внутри Mongo-документа характеристики embedded, потому что они читаются вместе и принадлежат одному товару.

Не переносим в MongoDB весь Product: цена, остаток и категория уже защищены SQL-ограничениями и участвуют в существующих операциях проекта.

Существующий Product.specs оставляем для небольшого общего контракта: вес, цвет и теги. В product_attributes храним только изменчивые поля конкретной категории, например тип переключателей клавиатуры или частоту обновления монитора. Одну характеристику не дублируем в двух базах.

Архитектура проекта

flowchart LR F["FastAPI"] --> PRODUCT_API["/products"] PRODUCT_API --> SA["SQLAlchemy"] SA --> PG[("PostgreSQL")] F --> ATTR_API["/products/{id}/attributes"] ATTR_API --> CHECK["ProductDep"] CHECK --> PG ATTR_API --> PM["PyMongo Async"] PM --> MDB[("MongoDB")]

Сначала ProductDep проверяет существование товара в PostgreSQL. Затем endpoint читает или изменяет только MongoDB-документ с его расширенными характеристиками.

Motor больше не используем. Асинхронный драйвер предоставляет официальный AsyncMongoClient из PyMongo.

Один клиент на lifespan

app/lifespan.py

from contextlib import asynccontextmanager
from typing import AsyncIterator

from fastapi import FastAPI
from pymongo import AsyncMongoClient
from sqlalchemy import select

from app.database import create_database_engine, create_session_factory
from app.models import User
from app.mongodb import ensure_product_attribute_indexes
from app.security import hash_password


@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[None]:
    settings = app.state.settings
    engine = create_database_engine(settings.database_url)
    app.state.engine = engine
    app.state.session_factory = create_session_factory(engine)

    mongo_client: AsyncMongoClient | None = None
    app.state.mongo_database = None

    try:
        if settings.admin_username is not None:
            password = settings.admin_password
            if password is None:
                raise RuntimeError(
                    "Bootstrap admin password is not configured"
                )
            with app.state.session_factory() as session:
                admin = session.scalar(
                    select(User).where(
                        User.username == settings.admin_username
                    )
                )
                if admin is None:
                    session.add(User(
                        username=settings.admin_username,
                        role="admin",
                        hashed_password=hash_password(
                            password.get_secret_value()
                        ),
                    ))
                    session.commit()

        if settings.mongodb_url is not None:
            mongo_client = AsyncMongoClient(
                settings.mongodb_url,
                tz_aware=True,
            )
            await mongo_client.admin.command("ping")
            app.state.mongo_database = mongo_client[
                settings.mongodb_database
            ]
            await ensure_product_attribute_indexes(
                app.state.mongo_database
            )

        yield
    finally:
        if mongo_client is not None:
            await mongo_client.close()
        engine.dispose()

AsyncMongoClient создаётся один раз внутри event loop приложения, управляет пулом соединений и закрывается при shutdown. Параметр tz_aware=True сохраняет UTC timezone у дат после чтения BSON.

def get_mongo_database(request: Request) -> AsyncDatabase:

Схемы и ObjectId

app/schemas.py

from datetime import datetime


AttributeValue = str | int | float | bool


class ProductAttributesPut(BaseModel):
    attributes: dict[str, AttributeValue] = Field(
        min_length=1,
        max_length=50,
    )

    @field_validator("attributes")
    @classmethod
    def validate_keys(cls, value):
        if any("." in key or key.startswith("$") for key in value):
            raise ValueError("Недопустимое имя характеристики")
        return value


class ProductAttributesPatch(ProductAttributesPut):
    pass


class ProductAttributesRead(ProductAttributesPut):
    id: str
    product_id: int
    created_at: datetime
    updated_at: datetime

MongoDB хранит настоящий ObjectId, но HTTP API возвращает его как строку. Клиенту не нужно знать детали BSON.

Преобразование документа

app/routers/product_attributes.py

from typing import Any, Mapping


def attributes_to_read(
    document: Mapping[str, Any],
) -> ProductAttributesRead:
    payload = dict(document)
    payload["id"] = str(payload.pop("_id"))
    return ProductAttributesRead.model_validate(payload)

Преобразование сосредоточено в одной функции. В остальных endpoint не размазываем ручную работу с _id.

Создать или заменить характеристики

app/routers/product_attributes.py

from datetime import UTC, datetime

from fastapi import APIRouter
from pymongo import ReturnDocument


router = APIRouter(
    prefix="/products",
    tags=["Product attributes"],
)


@router.put(
    "/{product_id}/attributes",
    response_model=ProductAttributesRead,
)
async def put_product_attributes(
    product: ProductDep,
    payload: ProductAttributesPut,
    database: MongoDatabaseDep,
    _admin: AdminRoleDep,
) -> ProductAttributesRead:
    now = datetime.now(UTC)
    document = await database["product_attributes"].find_one_and_update(
        {"product_id": product.id},
        {
            "$set": {
                "attributes": payload.attributes,
                "updated_at": now,
            },
            "$setOnInsert": {"created_at": now},
        },
        upsert=True,
        return_document=ReturnDocument.AFTER,
    )
    return attributes_to_read(document)

PUT идемпотентен: первый запрос создаёт документ, следующие полностью заменяют набор характеристик. ProductDep не позволяет добавить их несуществующему товару.

Получение характеристик

@router.get(
    "/{product_id}/attributes",
    response_model=ProductAttributesRead,
)
async def get_product_attributes(
    product: ProductDep,
    database: MongoDatabaseDep,
) -> ProductAttributesRead:
    document = await database["product_attributes"].find_one(
        {"product_id": product.id}
    )
    if document is None:
        raise HTTPException(
            status_code=404,
            detail="Характеристики товара не найдены",
        )
    return attributes_to_read(document)

Основной GET /products/{product_id} остаётся быстрым SQL-endpoint. Расширенные характеристики клиент запрашивает отдельно только тогда, когда они нужны.

Частичное изменение и удаление

@router.patch(
    "/{product_id}/attributes",
    response_model=ProductAttributesRead,
)
async def patch_product_attributes(
    product: ProductDep,
    payload: ProductAttributesPatch,
    database: MongoDatabaseDep,
    _admin: AdminRoleDep,
) -> ProductAttributesRead:
    changes = {
        f"attributes.{key}": value
        for key, value in payload.attributes.items()
    }
    changes["updated_at"] = datetime.now(UTC)
    document = await database["product_attributes"].find_one_and_update(
        {"product_id": product.id},
        {"$set": changes},
        return_document=ReturnDocument.AFTER,
    )
    if document is None:
        raise HTTPException(404, "Характеристики не найдены")
    return attributes_to_read(document)


@router.delete("/{product_id}/attributes", status_code=204)
async def delete_product_attributes(
    product: ProductDep,
    database: MongoDatabaseDep,
    _admin: AdminRoleDep,
) -> None:
    result = await database["product_attributes"].delete_one(
        {"product_id": product.id}
    )
    if result.deleted_count == 0:
        raise HTTPException(404, "Характеристики не найдены")

PATCH обновляет только переданные ключи через dotted paths. Проверка имён в Pydantic не позволяет превратить пользовательский ключ в оператор MongoDB.

Индекс поддерживает контракт «один товар — один документ»

app/mongodb.py

from pymongo.asynchronous.database import AsyncDatabase


async def ensure_product_attribute_indexes(
    database: AsyncDatabase,
) -> None:
    await database["product_attributes"].create_index(
        "product_id",
        unique=True,
        name="uq_product_attributes_product_id",
    )

db.product_attributes
  .find({product_id: 42})
  .explain("executionStats")

Уникальный индекс одновременно ускоряет основной запрос и защищает от двух документов для одного товара. Индексы на отдельные характеристики добавляем только под реальные фильтры.

Атомарность и транзакции

  • PUT, PATCH и DELETE меняют один MongoDB-документ и атомарны;
  • мультидокументная транзакция для этого CRUD не нужна;
  • такие транзакции требуют replica set или sharded cluster;
  • учебный standalone-контейнер этой лекции их не поддерживает.

Правильная граница документа часто заменяет транзакцию между несколькими коллекциями. Не усложняем инфраструктуру без требования.

Между PostgreSQL и MongoDB нет общей транзакции

sequenceDiagram participant API as FastAPI participant PG as PostgreSQL participant OUT as Outbox Worker participant B as Message Broker participant MDB as MongoDB API->>PG: product deleted + outbox event PG-->>API: один commit OUT->>PG: прочитать событие OUT->>B: опубликовать B->>MDB: удалить product_attributes

Удаление Product сейчас не может атомарно удалить MongoDB-документ. До появления outbox потерянные attributes допустимы: они не видны через API, потому что каждый endpoint сначала проверяет ProductDep. Надёжную очистку реализуем после знакомства с брокером сообщений.

Итоги

  • PostgreSQL хранит обязательные и транзакционные данные Product.
  • MongoDB хранит необязательные характеристики с разной структурой.
  • product_id — ссылка уровня приложения, а не ForeignKey.
  • Pydantic ограничивает вход, а unique index защищает модель хранения.
  • PyMongo Async подключается один раз через lifespan.
  • Удаление между двумя базами потребует eventual consistency и outbox.
