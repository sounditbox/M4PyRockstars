Лекция 8: Alembic в FastAPI — миграции схемы базы данных

В прошлой лекции мы подключили SQLAlchemy 2.0, описали ORM-модель Product и научили FastAPI работать с базой через одну Session на запрос.

Теперь сделаем следующий шаг: база данных получает историю изменений. Таблицы больше не появляются магически при старте приложения — их создаёт и обновляет отдельный управляемый процесс миграций.

Перед Alembic: подключаем PostgreSQL

Alembic будет подключаться к той же базе, что и приложение. Поэтому сначала разберём PostgreSQL-подключение.

Что нужно Пример
запущенный PostgreSQL локально, в Docker или в облаке
Python-драйвер psycopg
URL подключения postgresql+psycopg://...

Устанавливаем PostgreSQL-драйвер

uv add "psycopg[binary]"

Для SQLite отдельный пакет не нужен: драйвер входит в стандартную библиотеку Python. Для PostgreSQL ставим внешний DBAPI-драйвер, через который SQLAlchemy будет отправлять SQL в базу.

DATABASE_URL для PostgreSQL

# .env
DATABASE_URL=postgresql+psycopg://postgres:postgres@localhost:5432/products
Часть URL Смысл
postgresql+psycopg диалект SQLAlchemy + драйвер
postgres:postgres пользователь и пароль
localhost:5432 адрес и порт PostgreSQL
products имя базы данных

Код приложения менять не нужно: Settings.database_url отдаст новый URL в фабрику Engine.

Что такое миграция

Миграция — это файл с Python-кодом, который переводит схему базы из одного состояния в другое.

base
  ↓
001_create_products_table
  ↓
002_add_stock_count
  ↓
003_create_categories_table
  ↓
head

Каждый шаг знает, как двигаться вперёд через upgrade(). Если откаты нужны проекту, тот же файл описывает обратное движение через downgrade().

Что такое Alembic

Alembic — официальный инструмент миграций для проектов на SQLAlchemy.

  • читает текущую схему базы данных.
  • читает Base.metadata из ORM-моделей.
  • умеет сгенерировать кандидат миграции через --autogenerate.
  • применяет миграции в правильном порядке.
  • хранит текущую ревизию базы в таблице alembic_version.

Главная идея Alembic

ORM-модели описывают желаемую схему
        ↓
Alembic сравнивает metadata и реальную базу
        ↓
создаётся revision-файл
        ↓
разработчик проверяет файл руками
        ↓
alembic upgrade head применяет изменения

Ключевой момент — «проверяет руками». Autogenerate экономит время, но не заменяет мышление разработчика. Маленький робот-черновик, не архитектор.

Команды Alembic

Команда Зачем нужна
alembic init alembic один раз создать папку миграций
alembic revision --autogenerate -m "message" создать черновик миграции по моделям
alembic upgrade head применить миграции до последней версии
alembic downgrade -1 откатить одну миграцию назад
alembic current посмотреть ревизию текущей базы
alembic check проверить, не забыли ли миграцию

Установка и init

uv add alembic
alembic init alembic

init создаёт alembic.ini, alembic/env.py и папку alembic/versions/. Эти файлы коммитятся в проект.

Настраиваем alembic.ini

alembic.ini

[alembic]
script_location = %(here)s/alembic
prepend_sys_path = .
path_separator = os

# sqlalchemy.url здесь не задаём:
# реальный URL env.py возьмёт из Settings.

Это работает потому, что ниже мы меняем env.py: если URL не задан в alembic.ini, Alembic берёт Settings.database_url.

Полный env.py

alembic/env.py

from logging.config import fileConfig

from alembic import context
from sqlalchemy import engine_from_config, pool

from app.core.config import get_settings
from app.models import Base


config = context.config

if config.config_file_name is not None:
    fileConfig(config.config_file_name)

target_metadata = Base.metadata


def get_database_url() -> str:
    configured_url = config.get_main_option("sqlalchemy.url")
    if configured_url:
        return configured_url
    return get_settings().database_url


def get_alembic_section(database_url: str) -> dict[str, str]:
    section = config.get_section(
        config.config_ini_section, {}
    )
    section["sqlalchemy.url"] = database_url
    return section


def is_sqlite(database_url: str) -> bool:
    return database_url.startswith("sqlite")


def run_migrations_offline() -> None:
    database_url = get_database_url()
    context.configure(
        url=database_url,
        target_metadata=target_metadata,
        literal_binds=True,
        dialect_opts={"paramstyle": "named"},
        compare_type=True,
        render_as_batch=is_sqlite(database_url),
    )

    with context.begin_transaction():
        context.run_migrations()


def run_migrations_online() -> None:
    database_url = get_database_url()
    connectable = engine_from_config(
        get_alembic_section(database_url),
        prefix="sqlalchemy.",
        poolclass=pool.NullPool,
    )

    try:
        with connectable.connect() as connection:
            context.configure(
                connection=connection,
                target_metadata=target_metadata,
                compare_type=True,
                render_as_batch=is_sqlite(database_url),
            )

            with context.begin_transaction():
                context.run_migrations()
    finally:
        connectable.dispose()


if context.is_offline_mode():
    run_migrations_offline()
else:
    run_migrations_online()

target_metadata = Base.metadata даёт Alembic схему из ORM-моделей. Если модели разнесены по файлам, импортируйте их до чтения target_metadata.

compare_type=True учитывает изменения типов, а render_as_batch помогает SQLite с изменением таблиц.

Naming convention для ограничений

naming_convention даёт предсказуемые имена primary key, foreign key, unique, check и index. Alembic проще изменить или удалить constraint, если его имя не зависит от конкретной СУБД.

pk_products
ix_products_name
fk_products_category_id_categories

Обновляем Base

app/models.py

from sqlalchemy import MetaData
from sqlalchemy.orm import DeclarativeBase


naming_convention = {
    "ix": "ix_%(column_0_label)s",
    "uq": "uq_%(table_name)s_%(column_0_name)s",
    "ck": "ck_%(table_name)s_%(column_0_name)s",
    "fk": (
        "fk_%(table_name)s_%(column_0_name)s_"
        "%(referred_table_name)s"
    ),
    "pk": "pk_%(table_name)s",
}


class Base(DeclarativeBase):
    metadata = MetaData(naming_convention=naming_convention)

Добавляйте convention до первой миграции. Если поменять имена ограничений позже, Alembic может увидеть это как изменение схемы и сгенерировать лишние операции.

Убираем create_all из lifespan

app/lifespan.py

from collections.abc import AsyncIterator
from contextlib import asynccontextmanager

from fastapi import FastAPI

from app.database import (
    create_database_engine,
    create_session_factory,
)


@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[None]:
    settings = app.state.settings
    engine = create_database_engine(settings.database_url)
    session_factory = create_session_factory(engine)

    app.state.engine = engine
    app.state.session_factory = session_factory

    try:
        yield
    finally:
        engine.dispose()

Если база не мигрирована, запросы честно упадут с ошибкой уровня базы. Это лучше, чем тихо менять схему при каждом запуске API.

Создаём первую миграцию

alembic revision --autogenerate -m "create products table"

Alembic сравнит пустую базу и Base.metadata, увидит таблицу products и создаст новый файл в alembic/versions/.

alembic/versions/
└── 7f4c2e9a1b01_create_products_table.py

Имя и revision id будут другими на вашей машине. Это нормально: важна цепочка через down_revision.

Что autogenerate сравнивает

Обычно видит Требует внимания
добавление и удаление таблиц переименование таблицы может выглядеть как drop + create
добавление и удаление столбцов переименование столбца может выглядеть как drop + add
изменение nullable существующие данные могут нарушить новое ограничение
часть индексов, unique и foreign key безымянные constraints сложно менять
изменение типа при compare_type=True сложные преобразования данных нужно писать вручную

Autogenerate создаёт кандидата миграции. Перед применением читаем файл полностью.

Как исправить переименование

Если вы переименовали поле модели, Alembic может сгенерировать опасный черновик: drop_column("name") и add_column("title"). Это удалит данные из старого столбца.

Такой черновик правим руками на rename-операцию:

def upgrade() -> None:
    op.alter_column(
        "products",
        "name",
        new_column_name="title",
        existing_type=sa.String(length=80),
        existing_nullable=False,
    )


def downgrade() -> None:
    op.alter_column(
        "products",
        "title",
        new_column_name="name",
        existing_type=sa.String(length=80),
        existing_nullable=False,
    )

Для таблицы используется op.rename_table("old_name", "new_name"). Правило простое: переименование не должно выглядеть как удаление и создание заново.

Читаем файл ревизии

Каждый revision-файл содержит метаданные и две функции:

Часть Что означает
revision id текущей миграции
down_revision предыдущая миграция или None для первой
upgrade() изменения при движении вперёд
downgrade() изменения при откате назад

Alembic применяет не «все файлы подряд по имени», а граф ревизий через down_revision.

Применяем миграцию

alembic upgrade head

head означает «последняя доступная миграция». Для чистой SQLite-базы команда создаст таблицу products, индексы и служебную таблицу alembic_version.

INFO  [alembic.runtime.migration] Running upgrade  -> 7f4c2e9a1b01, create products table

После этого FastAPI-приложение может стартовать без create_all(): схема уже подготовлена.

Что такое alembic_version

Alembic хранит текущую ревизию базы в отдельной таблице:

alembic_version
┌────────────────┐
│ version_num    │
├────────────────┤
│ 7f4c2e9a1b01   │
└────────────────┘

Когда вы запускаете upgrade head, Alembic смотрит на эту таблицу, понимает текущую точку и применяет только недостающие миграции.

Это важнее, чем дата файла или порядок в папке. Истина — revision graph и alembic_version.

Второе изменение модели

Добавим запас товара на складе. Сначала меняется ORM-модель:

app/models.py

class Product(Base):
    __tablename__ = "products"

    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(80), index=True)
    category: Mapped[str] = mapped_column(String(40), index=True)
    price: Mapped[Decimal] = mapped_column(Numeric(12, 2))
    sale_price: Mapped[Decimal | None] = mapped_column(
        Numeric(12, 2), nullable=True
    )
    description: Mapped[str | None] = mapped_column(
        String(500), nullable=True
    )
    is_available: Mapped[bool] = mapped_column(Boolean, default=True)
    stock_count: Mapped[int] = mapped_column(default=0)
    specs: Mapped[dict[str, object] | None] = mapped_column(
        JSON, nullable=True
    )

После изменения модели база сама не меняется. Нужна новая миграция.

Генерируем вторую миграцию

alembic revision --autogenerate -m "add product stock count"

Ожидаемый черновик может выглядеть так:

def upgrade() -> None:
    op.add_column(
        "products",
        sa.Column("stock_count", sa.Integer(), nullable=False),
    )


def downgrade() -> None:
    op.drop_column("products", "stock_count")

На пустой базе это может пройти. На базе с существующими товарами — нет, потому что для старых строк неизвестно значение stock_count.

Ловушка NOT NULL-колонки

products
┌────┬──────────┐
│ id │ name     │
├────┼──────────┤
│ 1  │ Keyboard │
│ 2  │ Mouse    │
└────┴──────────┘

ALTER TABLE products
ADD COLUMN stock_count INTEGER NOT NULL

Что поставить в stock_count для старых строк?

ORM-параметр default=0 помогает при новых INSERT через SQLAlchemy, но не всегда означает, что база сможет заполнить старые строки во время миграции.

Безопасная миграция для stock_count

Один из простых вариантов — добавить временный server default, а затем убрать его:

def upgrade() -> None:
    op.add_column(
        "products",
        sa.Column(
            "stock_count",
            sa.Integer(),
            nullable=False,
            server_default="0",
        ),
    )
    op.alter_column(
        "products",
        "stock_count",
        server_default=None,
    )


def downgrade() -> None:
    op.drop_column("products", "stock_count")

Так существующие строки получают 0, а новые значения дальше контролирует приложение. В более сложных случаях делают миграцию в несколько шагов: добавить nullable-колонку, заполнить данные, потом включить NOT NULL.

Фикстура с Alembic

В тестах запускаем миграции на отдельном SQLite-файле из tmp_path, а потом создаём приложение с тем же database_url.

tests/conftest.py

from pathlib import Path

import pytest
from alembic import command
from alembic.config import Config
from fastapi import FastAPI

from app.core.config import Settings, get_settings
from app.main import create_app


PROJECT_ROOT = Path(__file__).resolve().parents[1]


def run_migrations(database_url: str) -> None:
    alembic_config = Config(str(PROJECT_ROOT / "alembic.ini"))
    alembic_config.set_main_option(
        "sqlalchemy.url",
        database_url.replace("%", "%%"),
    )
    command.upgrade(alembic_config, "head")


@pytest.fixture
def app(tmp_path: Path) -> FastAPI:
    database_path = tmp_path / "test.db"
    settings = Settings(
        app_name="Products API Test",
        api_prefix="/api/v1",
        database_url=f"sqlite+pysqlite:///{database_path.as_posix()}",
        jwt_secret_key="test-secret-not-for-production",
    )

    run_migrations(settings.database_url)

    application = create_app(settings)
    application.dependency_overrides[get_settings] = lambda: settings
    return application

set_main_option() передаёт тестовый URL в env.py. Замена % на %% нужна из-за особенностей configparser.

Минимальный workflow

1. Меняем ORM-модель
2. alembic revision --autogenerate -m "..."
3. Читаем и правим migration-файл
4. alembic upgrade head
5. alembic check
6. pytest
7. Коммитим код модели и migration-файл вместе

Модель без миграции — половина изменения. Миграция без модели — тоже половина. Обычно они живут в одном коммите.

Практика

Задача: перевести проект с create_all() на управляемые Alembic-миграции.

  1. Установите Alembic через uv add alembic.
  2. Инициализируйте Alembic-среду командой alembic init alembic.
  3. Очистите sqlalchemy.url в alembic.ini или настройте его так, чтобы URL не дублировался с Settings.
  4. В app/models.py добавьте naming_convention в Base.metadata.
  5. Настройте alembic/env.py: импортируйте Base, передайте target_metadata, включите compare_type=True и render_as_batch для SQLite.
  6. Удалите Base.metadata.create_all(bind=engine) из lifespan.
  7. Создайте первую миграцию create products table через --autogenerate.
  8. Проверьте migration-файл руками: таблица, индексы, nullable, downgrade.
  9. Примените миграции командой alembic upgrade head.
  10. Переведите тестовую фикстуру на запуск Alembic-миграций в SQLite-файле из tmp_path.
  11. Добавьте поле stock_count, создайте вторую миграцию и обработайте NOT NULL для существующих строк.
  12. Проверьте alembic check и весь набор тестов.

Дополнительная задача: проверьте откат второй миграции через downgrade -1, затем снова примените upgrade head.

Итоги

На этой лекции мы научились:

  • понимать, почему create_all() не заменяет миграции.
  • создавать Alembic-среду и подключать её к FastAPI-проекту.
  • использовать Base.metadata как источник желаемой схемы.
  • задавать naming_convention для стабильных constraint-имён.
  • создавать, читать и применять revision-файлы.
  • понимать ограничения autogenerate.
  • безопаснее добавлять NOT NULL-колонки к таблицам с данными.
  • учитывать особенности SQLite через batch mode.
  • запускать реальные миграции в тестах.
  • проверять schema drift через alembic check.

На следующей лекции добавим связи между таблицами: ForeignKey, relationship(), категории товаров и загрузку связанных данных без случайного N+1.
