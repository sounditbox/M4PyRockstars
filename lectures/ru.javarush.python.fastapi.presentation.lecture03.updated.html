Лекция 3: Pydantic v2 — схемы, вложенные модели и валидаторы

В первых двух лекциях Pydantic уже проверял тела запросов и формировал ответы. Теперь разберём его как самостоятельный инструмент проектирования контрактов данных.

Уточним разницу между обязательным, nullable-полем и значением по умолчанию, научимся переиспользовать ограничения, описывать вложенные структуры, писать валидаторы одного и нескольких полей и безопасно проверять результат частичного обновления.

Все примеры используют синтаксис Pydantic v2 и развивают тот же Products API.

Стартовая точка

К началу занятия у нас есть полный CRUD и три схемы: создание, частичное обновление и ответ API.

from pydantic import BaseModel, Field


class ProductCreate(BaseModel):
    name: str = Field(min_length=3, max_length=80)
    category: str = Field(min_length=2, max_length=40)
    price: float = Field(gt=0)
    description: str | None = None
    is_available: bool = True


class ProductUpdate(BaseModel):
    name: str | None = Field(default=None, min_length=3, max_length=80)
    category: str | None = Field(default=None, min_length=2, max_length=40)
    price: float | None = Field(default=None, gt=0)
    description: str | None = None
    is_available: bool | None = None


class ProductRead(ProductCreate):
    id: int

Эти модели работают, но ограничения повторяются, структура товара пока плоская, а правила между несколькими полями никак не выражены.

Что такое Pydantic

Pydantic — библиотека Python для проверки, преобразования и сериализации данных на основе аннотаций типов.

Модель Pydantic описывает ожидаемую структуру данных: названия полей, их типы, значения по умолчанию и дополнительные ограничения.

В FastAPI Pydantic используется, чтобы:

  • проверять тела запросов и преобразовывать входные значения.
  • возвращать подробные ошибки валидации.
  • проверять и фильтровать ответы API.
  • создавать JSON Schema для OpenAPI и Swagger UI.

Аннотации типов сами по себе не проверяют данные во время выполнения Python. Эту проверку выполняет Pydantic при создании или валидации модели.

Что делает Pydantic

Этап Что происходит Пример
Parsing чтение входных Python/JSON-данных {"price": "99.5"}
Validation проверка типов, ограничений и пользовательских правил price > 0
Coercion допустимое преобразование типов "99.5" → 99.5
Serialization преобразование модели в словарь или JSON model_dump()
JSON Schema описание структуры для OpenAPI схемы в /docs

Аннотация типа описывает ожидаемое значение во время выполнения Pydantic, а не только подсказывает IDE.

Обязательное, nullable и значение по умолчанию

class ProductExample(BaseModel):
    name: str
    description: str | None
    category: str = "other"
    note: str | None = None
Поле Можно не передавать? Можно передать null?
name: str нет нет
description: str | None нет да
category: str = "other" да нет
note: str | None = None да да

Ключевое правило: возможность пропустить поле задаёт значение по умолчанию, а | None только разрешает значение null.

Преобразование типов и strict mode

По умолчанию Pydantic работает в мягком режиме и преобразует данные, если это безопасно и предусмотрено таблицей преобразований.

class StockInfo(BaseModel):
    quantity: int


stock = StockInfo.model_validate({"quantity": "12"})
print(stock.quantity)  # 12, тип int

Если неявное преобразование нежелательно, ограничение можно сделать строгим.

class StrictStockInfo(BaseModel):
    quantity: int = Field(ge=0, strict=True)


StrictStockInfo(quantity=12)    # корректно
StrictStockInfo(quantity="12")  # ValidationError

Strict mode стоит включать осознанно. Для HTTP path/query-параметров преобразование строк естественно, а для некоторых полей JSON-контракта строгий тип помогает раньше заметить ошибку клиента.

Field и переиспользуемые типы

from typing import Annotated

from pydantic import BaseModel, Field


ProductName = Annotated[
    str,
    Field(min_length=3, max_length=80, examples=["Mechanical Keyboard"]),
]
CategoryName = Annotated[
    str,
    Field(min_length=2, max_length=40, pattern=r"^[a-z0-9-]+$"),
]
PositivePrice = Annotated[float, Field(gt=0, le=1_000_000)]


class ProductBase(BaseModel):
    name: ProductName
    category: CategoryName
    price: PositivePrice

Annotated сохраняет основной Python-тип и прикрепляет к нему метаданные Pydantic. Такой тип можно переиспользовать в нескольких моделях без копирования одинаковых ограничений.

Схема зависит от сценария

class ProductBase(BaseModel):
    name: ProductName
    category: CategoryName
    price: PositivePrice
    description: str | None = Field(default=None, max_length=500)
    is_available: bool = True


class ProductCreate(ProductBase):
    pass


class ProductUpdate(BaseModel):
    name: ProductName | None = None
    category: CategoryName | None = None
    price: PositivePrice | None = None
    description: str | None = Field(default=None, max_length=500)
    is_available: bool | None = None


class ProductRead(ProductBase):
    id: int
Схема Назначение
ProductBase общие публичные поля и ограничения
ProductCreate данные, которые клиент присылает при создании
ProductUpdate поля, которые можно частично изменить
ProductRead публичный ответ API с серверным ID

Наследование полезно, когда смысл полей совпадает. Не нужно строить глубокую иерархию только ради устранения двух повторяющихся строк.

Вложенные модели и коллекции

Tag = Annotated[str, Field(min_length=2, max_length=30)]


class ProductSpecs(BaseModel):
    weight_grams: int = Field(gt=0)
    color: str | None = Field(default=None, max_length=30)
    tags: list[Tag] = Field(default_factory=list, max_length=10)


class ProductBase(BaseModel):
    name: ProductName
    category: CategoryName
    price: PositivePrice
    description: str | None = Field(default=None, max_length=500)
    is_available: bool = True
    specs: ProductSpecs | None = None

{
  "name": "Mechanical Keyboard",
  "category": "electronics",
  "price": 99.0,
  "specs": {
    "weight_grams": 850,
    "color": "black",
    "tags": ["wireless", "mechanical"]
  }
}

Pydantic рекурсивно проверит объект specs, длину списка и каждый элемент tags. default_factory=list явно создаёт новый список для каждого экземпляра модели.

ConfigDict: конфигурация модели

ConfigDict — типизированный словарь с настройками поведения всей Pydantic-модели. Он задаётся в атрибуте класса model_config и применяется ко всем его полям.

from pydantic import BaseModel, ConfigDict


class ProductCreate(ProductBase):
    model_config = ConfigDict(
        extra="forbid",
        str_strip_whitespace=True,
        validate_assignment=True,
    )

Настройка наследуется дочерними моделями и при необходимости может быть переопределена. Не нужно включать все параметры сразу: конфигурация должна отражать конкретный контракт модели.

Основные параметры ConfigDict

Параметр Что меняет
extra поведение неизвестных полей: "ignore", "forbid" или "allow"
str_strip_whitespace удаляет пробелы в начале и конце всех строковых полей
validate_assignment повторно валидирует поле при присваивании после создания модели
strict включает строгую проверку типов для всей модели
frozen запрещает изменение экземпляра после создания
from_attributes позволяет строить схему из атрибутов объекта, например ORM-модели
json_schema_extra добавляет примеры и другие данные в JSON Schema/OpenAPI

Часть настроек можно задавать точечно через Field. ConfigDict нужен, когда правило относится ко всей модели.

extra: что делать с неизвестными полями

Значение Поведение Когда подходит
"ignore" лишние поля игнорируются; это значение по умолчанию мягкая обратная совместимость
"forbid" лишнее поле вызывает ошибку валидации строгие входные контракты API
"allow" лишние поля сохраняются в __pydantic_extra__ динамические структуры, где это действительно ожидается

Без extra="forbid" неизвестное поле обычно будет проигнорировано. Это может скрыть опечатку клиента.

{
  "name": "Keyboard",
  "category": "electronics",
  "price": 99,
  "is_avaliable": true
}

Здесь клиент ошибся в имени is_available. При extra="forbid" он сразу получит ошибку валидации вместо успешного ответа с проигнорированным значением.

field_validator: как он устроен

field_validator связывает метод класса с одним или несколькими полями. Метод получает значение, проверяет или преобразует его и обязательно возвращает результат.

from pydantic import field_validator


class ProductBase(BaseModel):
    name: ProductName
    category: CategoryName
    price: PositivePrice

    @field_validator("name")
    @classmethod
    def normalize_name(cls, value: str) -> str:
        normalized = " ".join(value.split())

        if normalized.lower() in {"test", "product", "товар"}:
            raise ValueError("Укажите содержательное название товара")

        return normalized

Здесь валидатор нормализует строку и затем проверяет содержательное правило, которое нельзя выразить только через Field.

Как формируется field_validator

  1. @field_validator("name") указывает поле; можно передать несколько имён.
  2. @classmethod ставится под декоратором Pydantic: первым аргументом метода становится cls.
  3. value содержит текущее значение. Его тип зависит от выбранного mode.
  4. Метод возвращает проверенное или преобразованное значение.
  5. При нарушении правила поднимают ValueError; Pydantic добавляет его в общую ошибку валидации.

При необходимости третьим аргументом можно принять ValidationInfo: он даёт имя текущего поля, контекст и уже проверенные поля, объявленные выше.

Подсказка по mode

after — после стандартной проверки, используется по умолчанию; before — для сырых входных данных; plain — заменяет дальнейшую проверку Pydantic; wrap — оборачивает весь процесс валидации. В большинстве задач выбирайте after.

model_validator: правило нескольких полей

from typing import Self

from pydantic import model_validator


class ProductCreate(ProductBase):
    sale_price: PositivePrice | None = None

    @model_validator(mode="after")
    def check_sale_price(self) -> Self:
        if self.sale_price is not None and self.sale_price >= self.price:
            raise ValueError("Цена со скидкой должна быть меньше обычной цены")

        return self

model_validator проверяет данные модели целиком. Он подходит для правил, где одно поле зависит от другого: диапазон дат, совпадение паролей, минимальная и максимальная цена.

В примере выбран mode="after": отдельные поля уже проверены, метод получает созданный экземпляр через self и обязан вернуть его.

Подсказка по mode

after получает готовую модель и подходит для обычных межполевых правил; before получает сырые данные до создания модели; wrap позволяет управлять запуском внутренней валидации и перехватывать её ошибки.

PATCH: проверяем состояние после слияния

В PATCH клиент может прислать только sale_price. Модель запроса не знает текущую обычную цену товара, поэтому межполевое правило нужно проверить после объединения данных.

@app.patch(
    "/products/{product_id}",
    response_model=ProductRead,
    tags=["products"],
)
def update_product(product_id: int, product_data: ProductUpdate):
    product = get_product_or_404(product_id)

    update_data = product_data.model_dump(exclude_unset=True)
    candidate_data = product.model_dump(exclude={"id"}) | update_data

    validated = ProductCreate.model_validate(candidate_data)
    updated_product = ProductRead(
        id=product_id,
        **validated.model_dump(),
    )

    products_db[product_id] = updated_product
    return updated_product

ProductUpdate проверяет форму частичного запроса, а ProductCreate.model_validate(...) проверяет полное итоговое состояние ресурса.

Ошибки валидации Pydantic

Pydantic собирает ошибки всех полей и поднимает одно исключение ValidationError. Получить структурированный список можно через метод errors().

from pydantic import ValidationError


try:
    ProductCreate.model_validate(raw_data)
except ValidationError as error:
    print(error.error_count())
    print(error.errors())
Где возникла ошибка Что произойдёт
ручной вызов model_validate() код получает ValidationError и сам решает, как его обработать
body, query, path или другой вход эндпоинта FastAPI перехватывает ошибку запроса и обычно возвращает 422
ValueError внутри валидатора Pydantic включает сообщение в общий ValidationError
ответ эндпоинта не соответствует выходной схеме это ошибка серверного кода; клиент не должен получать 422 за некорректный ответ сервера

Не перехватывайте ValidationError без необходимости внутри обычного FastAPI-эндпоинта: стандартный обработчик уже формирует согласованный ответ для клиента.

Как устроена отдельная ошибка

{
  "type": "greater_than",
  "loc": ["price"],
  "msg": "Input should be greater than 0",
  "input": -10,
  "ctx": {"gt": 0.0}
}
Ключ Смысл
loc путь до ошибочного поля; FastAPI добавляет источник вроде body, query или path
type машиночитаемый тип ошибки
msg человекочитаемое объяснение
input значение, которое не прошло проверку
ctx дополнительные параметры правила, если они есть

В автотестах надёжнее проверять статус, loc и type, а не целиком сравнивать английский текст msg, который может измениться между версиями.

model_validate и model_dump

product = ProductCreate.model_validate(raw_data)

python_data = product.model_dump()
json_ready_data = product.model_dump(mode="json")
json_string = product.model_dump_json()

changes = product_update.model_dump(exclude_unset=True)
Метод Результат
model_validate(data) проверенная модель из словаря или объекта
model_dump() словарь с Python-значениями
model_dump(mode="json") словарь со значениями, совместимыми с JSON
model_dump_json() готовая JSON-строка

exclude_unset=True уже использовался в лекции 2 для PATCH; теперь мы видим его место в общем API сериализации Pydantic.

Входная, внутренняя и выходная схемы

Один и тот же товар выглядит по-разному в запросе клиента, внутри приложения и в публичном ответе. Разные схемы фиксируют эти разные контракты.

Схема Определение Зачем отделять
Входная данные, которые API разрешает принять от клиента клиент не должен назначать серверные и внутренние поля; создание и обновление требуют разных наборов данных
Внутренняя полное представление данных, с которым работает приложение или хранилище может содержать закупочную цену, служебные статусы, хэши и другие непубличные поля
Выходная публичный контракт ответа API защищает от утечки внутренних данных и стабилизирует формат для клиента

Разделение нужно из-за разных уровней доверия, владельцев полей и требований к видимости. Оно также позволяет менять внутреннее устройство приложения, не ломая публичный контракт API.

Как выходная схема защищает ответ

class ProductRead(ProductBase):
    id: int


class ProductInternal(ProductRead):
    supplier_code: str
    purchase_price: PositivePrice


@app.get(
    "/products/{product_id}",
    response_model=ProductRead,
    tags=["products"],
)
def get_product(product_id: int):
    return ProductInternal(
        id=product_id,
        name="Mechanical Keyboard",
        category="electronics",
        price=99,
        supplier_code="SUP-4815",
        purchase_price=55,
    )

response_model проверит, сериализует и отфильтрует ответ. Поля supplier_code и purchase_price не попадут во внешний JSON.

Выходная схема — это не просто документация, а граница утечки внутренних данных.

Куда поместить правило валидации

Правило Где проверять
цена положительная Field(gt=0)
название не состоит из пробелов field_validator
цена со скидкой меньше обычной model_validator
товар с таким именем уже существует сервис/эндпоинт после обращения к хранилищу
категория существует в базе данных сервисный слой, а не Pydantic-модель

Pydantic хорошо проверяет самодостаточные данные. Правила, которым нужны база данных, текущий пользователь или внешний сервис, не стоит прятать в валидаторы модели.

Итоговая структура схем Products API

Уровень Элементы Роль
Переиспользуемые типы ProductName, CategoryName, PositivePrice, Tag общие типы и ограничения полей
Вложенная схема ProductSpecs характеристики товара и список тегов
Общая основа ProductBase публичные поля, общие ограничения и field_validator
Входные схемы ProductCreate
ProductUpdate		 создание полного состояния и частичное обновление через PATCH
Выходная схема ProductRead наследует ProductBase и добавляет серверный id
Внутренняя схема ProductInternal расширяет публичную схему служебными полями, скрытыми через response_model

ProductCreate, ProductRead и ProductInternal переиспользуют общую основу. ProductUpdate остаётся отдельной схемой, потому что все разрешённые для изменения поля должны быть необязательными.

Выносим схемы из main.py

До этого весь код находился в одном файле: создание приложения, Pydantic-схемы, хранилище и эндпоинты. После появления нескольких схем main.py становится трудно читать.

Практика

Задача: усилить контракты данных существующего Products API и проверить изменения через Swagger UI.

  1. Вынесите повторяющиеся ограничения в типы ProductName, CategoryName и PositivePrice через Annotated.
  2. Добавьте вложенную модель ProductSpecs с полями weight_grams, color и tags.
  3. Запретите неизвестные поля в ProductCreate через ConfigDict(extra="forbid").
  4. Добавьте field_validator, который убирает повторяющиеся пробелы из названия и запрещает названия test, product и товар.
  5. Добавьте поля sale_price и проверку, что цена со скидкой меньше обычной цены.
  6. Обновите PATCH: после слияния старых и новых данных повторно провалидируйте полное состояние товара.
  7. Перенесите типы и Pydantic-схемы из main.py в app/schemas.py и обновите импорты.
  8. Проверьте в Swagger UI: лишнее поле, некорректный вложенный объект, слишком много тегов, запрещённое название и неверную цену со скидкой.

Дополнительная задача: добавьте внутреннюю схему с полем purchase_price и убедитесь, что оно не попадает в ответ с response_model=ProductRead.
