Уровень 14: очереди задач и масштабирование Celery

На этом уровне мы разделим уже существующие фоновые задачи по очередям и научимся запускать отдельные обработчики для разных типов нагрузки.

После занятия вы сможете объяснить роли producer, broker, queue и worker, создать несколько очередей средствами Celery и масштабировать их обработку.

Очередь отделяет постановку задачи от её выполнения

graph LR API[FastAPI
producer] --> B[RabbitMQ
broker] BEAT[Celery Beat
scheduler] -->|по расписанию| B B --> RQ((reports)) B --> MQ((maintenance)) RQ --> RW[celery-reports
worker] MQ --> MW[celery-maintenance
worker] RW --> REDIS[(Redis
results)] MW --> REDIS
  • Producer создаёт задачу. В проекте это FastAPI.
  • Broker хранит задачи до обработки. В проекте это RabbitMQ.
  • Queue группирует задачи одного типа.
  • Worker забирает и выполняет задачи. Celery worker и есть consumer.
  • Beat ставит периодические задачи по расписанию, но не выполняет их.

Отдельный consumer на aio-pika для Celery не нужен: Celery worker уже подписывается на очередь и подтверждает задачи сам.

В проекте достаточно двух очередей

  • reports — отчёты, которые могут выполняться долго.
  • maintenance — короткие служебные задачи, например ежедневная сводка каталога.

Если поместить всё в одну очередь, несколько долгих отчётов могут задержать короткую служебную задачу. Разные очереди позволяют обрабатывать их независимо.

Celery создаёт очереди из конфигурации

application.conf.update(
    task_create_missing_queues=True,
    task_routes={
        "app.tasks.generate_product_report": {
            "queue": "reports",
        },
        "app.tasks.build_catalog_summary": {
            "queue": "maintenance",
        },
    },
    task_default_queue="maintenance",
)

task_routes отвечает на простой вопрос: в какую очередь отправить задачу с данным именем. Благодаря task_create_missing_queues Celery сам объявит exchange, очередь и binding.

Обычная функция становится задачей через декоратор

@celery_app.task(name="app.tasks.generate_product_report")
def generate_product_report(...):
    ...

@celery_app.task(name="app.tasks.build_catalog_summary")
def build_catalog_summary():
    ...

FastAPI ставит отчёт в очередь вызовом:

task = generate_product_report.delay(
    category_slug=request.category_slug,
    only_available=request.only_available,
    limit=request.limit,
    simulate_work_seconds=request.simulate_work_seconds,
)

delay() быстро возвращает идентификатор задачи. Сам отчёт выполняется позже в worker.

Celery Beat ставит задачи по расписанию

beat_schedule={
    "catalog-summary-every-morning": {
        "task": "app.tasks.build_catalog_summary",
        "schedule": crontab(hour=8, minute=0),
    },
}

В 08:00 UTC Beat публикует build_catalog_summary. Затем task_routes направляет задачу в maintenance, а выполняет её celery-maintenance.

Beat — это планировщик, а не worker. Для практики ту же задачу отправим вручную, чтобы не ждать времени из расписания.

Каждый worker слушает только свою очередь

# Долгие отчёты: два одновременных процесса
celery -A app.celery_app:celery_app worker \
  --queues=reports --concurrency=2

# Короткие задачи: четыре одновременных процесса
celery -A app.celery_app:celery_app worker \
  --queues=maintenance --concurrency=4

В проекте команды уже записаны в сервисах celery-reports, celery-maintenance и celery-beat. Запускать их вручную не нужно.

--queues выбирает очередь, а --concurrency задаёт число задач, которые worker может выполнять одновременно.

Масштабирование — это добавление обработчиков

Если очередь reports растёт, можно увеличить concurrency или запустить дополнительные экземпляры того же worker:

docker compose up -d --scale celery-reports=3

RabbitMQ распределит задачи очереди reports между всеми подключёнными workers. Сначала нужно посмотреть на длину очереди и время выполнения задач, а уже затем масштабировать.

Prefetch определяет, сколько задач worker резервирует заранее. Это важная настройка, но на первом знакомстве оставим значение Celery по умолчанию и не будем смешивать её с маршрутизацией.

Практика

  1. Запустите окружение: docker compose up -d --build --wait.
  2. Откройте Swagger UI: http://localhost:8000/docs.
  3. Отправьте несколько отчётов с simulate_work_seconds=5.
  4. Убедитесь по логам celery-beat, что планировщик запущен и загрузил расписание.
  5. Отправьте короткую сводку в очередь maintenance: 
    docker compose exec celery-maintenance \
  celery -A app.celery_app:celery_app call \
  app.tasks.build_catalog_summary
  6. Откройте RabbitMQ Management: http://localhost:15672.
  7. Найдите очереди reports и maintenance.
  8. Посмотрите задачи и workers в Flower: http://localhost:5555.
  9. Увеличьте число celery-reports и сравните скорость обработки.

Что важно запомнить

  • FastAPI ставит задачу, RabbitMQ хранит её, Celery worker выполняет.
  • Worker — это consumer, поэтому отдельный consumer для Celery не нужен.
  • Разные типы нагрузки удобно разводить по разным очередям через task_routes.
  • Worker выбирает очередь флагом --queues.
  • Beat публикует периодические задачи, а выполняет их обычный worker.
  • Систему масштабируют увеличением concurrency или числа workers.

Дальше: acknowledgements, retries, priority, TTL и dead-letter queues стоит изучать после того, как базовая маршрутизация стала понятна.
