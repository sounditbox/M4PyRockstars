Лекция 7: SQLAlchemy 2.0 в FastAPI — модели, сессии и CRUD

In-memory-словарь исчезает при перезапуске процесса и не умеет обеспечивать транзакции, ограничения и конкурентный доступ. Перенесём товары в SQLite через современный API SQLAlchemy 2.0.

Сначала разберём Engine, ORM-модель и Session, затем перепишем CRUD и подключим базу к FastAPI через dependency injection.

Что такое SQLAlchemy

SQLAlchemy — Python-библиотека для работы с реляционными базами данных. В ней есть два тесно связанных уровня:

Уровень Назначение
SQL Expression Language / Core строит SQL-выражения и выполняет их через соединения
ORM связывает строки таблиц с Python-объектами

ORM не отменяет SQL. Она генерирует SQL и управляет состоянием объектов, но разработчику всё равно нужно понимать таблицы, ключи, индексы и транзакции.

SQL Expression Language

Запрос SQLAlchemy — не строка, а дерево Python-объектов, которое описывает SQL-конструкцию.

statement = (
    select(Product)
    .where(Product.category == "electronics")
    .where(Product.price < 100)
    .order_by(Product.price)
    .limit(20)
)

select(), where() и order_by() создают SQL expression objects. Пока мы только строим statement, запрос в базу ещё не отправляется.

Как выражение превращается в результат

Python-выражение
select(Product).where(Product.price < 100)
        ↓
дерево SQLAlchemy Expression Language
        ↓
dialect компилирует SQL под SQLite / PostgreSQL
        ↓
DBAPI driver отправляет SQL + параметры
        ↓
база выполняет запрос
        ↓
Result / ScalarResult / ORM-объекты

SQLAlchemy разделяет описание запроса и его выполнение. Один и тот же statement можно вывести для отладки, дополнить условиями и только потом передать в Session.

Запросы собираются композиционно

Методы statement работают в generative-стиле: возвращают новый объект с добавленной частью запроса.

statement = select(Product)

if category is not None:
    statement = statement.where(Product.category == category)

if only_available:
    statement = statement.where(
        Product.is_available.is_(True)
    )

statement = statement.order_by(Product.id)

Так удобно строить запрос из необязательных query-параметров. Исходный select(Product) не изменяется «на месте» — переменная получает новую версию statement.

Основные конструкции языка

SQLAlchemy Роль в SQL
select(Product) SELECT ... FROM products
.where(condition) WHERE
.join(Model) JOIN
.order_by(...) ORDER BY
.limit(n).offset(k) ограничение и смещение результата
insert(), update(), delete() явные DML-выражения
func.count(), func.sum() SQL-функции и агрегаты

В ORM обычные одиночные изменения чаще выражаются через работу с объектом и Session. Явные update() и delete() особенно полезны для массовых операций.

Python-операторы становятся SQL

Python-выражение SQL-смысл
Product.price > 100 price > :price_1
Product.category == "books" category = :category_1
Product.id.in_([1, 2, 3]) id IN (...)
Product.description.is_(None) description IS NULL
and_(a, b), or_(a, b) логические AND и OR

У class attributes вроде Product.price операторы перегружены: результатом сравнения становится SQL expression, а не обычный Python bool.

Связанные параметры вместо склейки строк

statement = select(Product).where(
    Product.category == category
)

Упрощённо SQLAlchemy скомпилирует выражение так:

SELECT products.id, products.name, products.category
FROM products
WHERE products.category = :category_1

Само значение category передаётся драйверу отдельно — как данные параметра, а не как SQL-код. Поэтому пользовательский ввод не становится исполняемым фрагментом запроса.

Не делайте так:

# Небезопасно: пользовательское значение склеено с SQL
sql = f"SELECT * FROM products WHERE category = '{category}'"

execute(), scalars() и scalar()

Вызов Возвращает Когда использовать
session.execute(statement) Result со строками Row выбрано несколько колонок или сущностей
session.scalars(statement) ScalarResult с первым элементом каждой строки нужен список ORM-объектов или значений одной колонки
session.scalar(statement) первый элемент первой строки или None нужно одно число, значение или первый объект 
statement = select(Product)

rows = session.execute(statement).all()
# [(Product(id=1, name="Keyboard"),),
#  (Product(id=2, name="Mouse"),)]

products = session.scalars(statement).all()
# [Product(id=1, name="Keyboard"),
#  Product(id=2, name="Mouse")]

execute() сохраняет структуру строк результата. Даже если выбран один ORM-класс, каждая строка содержит один элемент: (Product(...),).

scalars() снимает эту внешнюю строку и берёт первый элемент каждой строки. Он не преобразует данные в модели — ORM-объекты уже создала Session.

statement = select(Product.name, Product.price)

rows = session.execute(statement).all()
# [("Keyboard", Decimal("99.90")),
#  ("Mouse", Decimal("49.90"))]

names = session.scalars(statement).all()
# ["Keyboard", "Mouse"]
# price отброшен: scalars() берёт первый элемент строки

count = session.scalar(
    select(func.count(Product.id))
)
# 2

first_name = session.scalar(
    select(Product.name).order_by(Product.id)
)
# "Keyboard" или None, если строк нет

scalar() подходит для count(), sum() и других запросов с одним ожидаемым значением. Если важно потребовать ровно одну строку, используйте session.scalars(statement).one(); для варианта «ноль или одна» — one_or_none().

Raw SQL остаётся доступен

from sqlalchemy import text


statement = text(
    "SELECT * FROM products WHERE category = :category"
)
rows = session.execute(
    statement,
    {"category": category},
).all()

text() нужен для специфичного SQL, сложного отчёта или возможности базы, которую неудобно выразить другими конструкциями.

Даже в raw SQL значения передаются связанными параметрами. Expression Language обычно предпочтительнее: она композиционна, знает типы и адаптируется к dialect.

Основные объекты

database URL
    ↓
Engine ── connection pool ── DBAPI driver ── database
    ↑
Session ── transaction + identity map + ORM objects
    ↑
FastAPI dependency ── один HTTP-запрос
  • Engine знает, как подключаться к базе, и управляет пулом соединений.
  • ORM-модель описывает соответствие Python-класса таблице.
  • Session выполняет запросы и отслеживает изменения объектов в транзакции.
  • Driver реализует конкретный протокол: sqlite3, psycopg и другие.

Анатомия mapped-атрибута

name: Mapped[str] = mapped_column(String(80), index=True)
# ①       ②              ③
Часть Что означает
① name имя Python-атрибута; по умолчанию оно же станет именем SQL-столбца
② Mapped[str] ORM-атрибут, значение которого у экземпляра имеет Python-тип str
③ mapped_column(...) настройки столбца и ORM-маппинга: SQL-тип, индекс, ключи, default и другие параметры

Вместе левая и правая части дают SQLAlchemy достаточно информации, чтобы создать столбец таблицы и управляемый атрибут Python-класса.

Что такое Mapped[T]

Mapped — специальный generic-тип SQLAlchemy. Он помечает атрибут как часть ORM-маппинга и сообщает ожидаемый Python-тип значения.

id: Mapped[int]
name: Mapped[str]
description: Mapped[str | None]
  • Mapped[int] означает: у экземпляра модели product.id читается как int.
  • Mapped[str | None] разрешает значение None на уровне Python-типизации.
  • Аннотацию понимают SQLAlchemy, IDE, Pylance, mypy и другие type checkers.
  • Mapped не заменяет Pydantic и не валидирует входной HTTP JSON.

Тип T — это тип Python-значения, а не буквальное имя SQL-типа.

Атрибут класса и атрибут экземпляра

У mapped-атрибута два режима работы:

Product.price
# ORM-выражение: можно использовать в select() и where()

product = Product(price=99.90)
product.price
# Python-значение конкретного объекта
Выражение Смысл
Product.price > 100 SQLAlchemy строит условие SQL
product.price > 100 Python сравнивает значение загруженного объекта

SQLAlchemy заменяет обычный class attribute специальным descriptor. Благодаря этому одно имя работает и в запросах, и у экземпляров модели.

Что делает mapped_column()

mapped_column() — declarative-конструкция SQLAlchemy 2.0 для описания столбца внутри ORM-класса.

price: Mapped[Decimal] = mapped_column(
    Numeric(12, 2),
    nullable=False,
    index=True,
)

При объявлении класса SQLAlchemy:

  1. создаёт объект Column в Product.__table__.
  2. добавляет таблицу в Base.metadata.
  3. создаёт ORM-маппинг между столбцом и атрибутом Product.price.
  4. настраивает отслеживание изменений экземпляров внутри Session.

В declarative-моделях mapped_column() заменяет привычный для старых примеров Column() и лучше работает с современной типизацией.

Что SQLAlchemy выводит автоматически

Если тип и ограничения очевидны, SQLAlchemy умеет вывести SQL-тип и nullable из Mapped[...]:

class Example(Base):
    __tablename__ = "examples"

    id: Mapped[int] = mapped_column(primary_key=True)
    title: Mapped[str]
    note: Mapped[str | None]
Объявление Примерный результат в таблице
Mapped[int] + primary key INTEGER PRIMARY KEY NOT NULL
Mapped[str] VARCHAR NOT NULL
Mapped[str | None] VARCHAR NULL

Даже когда mapped_column() справа не указан, SQLAlchemy создаёт его неявно. В учебной модели мы оставляем явную правую часть там, где задаём длину, индекс, точность или другое ограничение.

Python-тип и SQL-тип

Mapped[T] описывает значение в Python. Первый позиционный аргумент mapped_column() может явно задавать тип столбца в базе:

Python / ORM SQLAlchemy type Типичная форма в БД
Mapped[int] Integer INTEGER
Mapped[str] String(80) VARCHAR(80)
Mapped[Decimal] Numeric(12, 2) NUMERIC(12, 2)
Mapped[bool] Boolean зависит от диалекта
Mapped[dict[str, object]] JSON JSON, JSONB или адаптация диалекта

Явный SQLAlchemy type имеет приоритет над типом, который можно было бы вывести из аннотации. Конкретный DDL затем адаптирует dialect выбранной базы.

None и nullable

required: Mapped[str]
# обычно NOT NULL

optional: Mapped[str | None]
# обычно NULL

explicit: Mapped[
    str | None
] = mapped_column(
    nullable=False
)
# Python-тип допускает None, но база отклонит NULL

Приоритет определения nullability:

  1. явный nullable=True или nullable=False.
  2. primary_key=True подразумевает NOT NULL.
  3. иначе | None внутри Mapped обычно означает NULL, а его отсутствие — NOT NULL.

Обычно Python-тип и ограничение базы лучше держать согласованными. Намеренное расхождение требует понятной причины.

Основные параметры mapped_column()

Параметр Назначение
primary_key=True столбец входит в первичный ключ
nullable=False запрещает SQL NULL
unique=True создаёт одиночное ограничение уникальности
index=True просит создать индекс для поиска и сортировки
default=... значение формируется на стороне Python при INSERT
server_default=... значение по умолчанию формирует сама база данных
ForeignKey(...) связывает столбец с ключом другой таблицы

index=True не означает «всегда быстрее»: индекс занимает место и замедляет запись. Его добавляют под реальные запросы.

default и server_default

from datetime import datetime

from sqlalchemy import DateTime, func


is_available: Mapped[bool] = mapped_column(default=True)
created_at: Mapped[datetime] = mapped_column(
    DateTime(timezone=True),
    server_default=func.now(),
)
default=True server_default=func.now()
SQLAlchemy подставляет значение в INSERT DDL задаёт default на стороне базы
работает, когда запись идёт через этот SQLAlchemy mapping работает и для других клиентов базы
не является значением обычного Python-атрибута сразу после Product() значение появляется после INSERT и может потребовать refresh

Не путайте оба варианта со значением по умолчанию в Pydantic-схеме: это ещё один, внешний слой контракта.

Имя атрибута и имя SQL-столбца

class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(
        "user_id",
        primary_key=True,
    )

В Python используем User.id, а в SQL столбец называется user_id. Если строковое имя не передано, SQLAlchemy берёт имя атрибута.

Разные имена полезны при подключении к существующей схеме, но в новом проекте одинаковые имена обычно проще.

ORM-модель товара

app/models.py

from decimal import Decimal

from sqlalchemy import JSON, Boolean, Numeric, String
from sqlalchemy.orm import Mapped, mapped_column


class Product(Base):
    __tablename__ = "products"

    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(80), index=True)
    category: Mapped[str] = mapped_column(String(40), index=True)
    price: Mapped[Decimal] = mapped_column(Numeric(12, 2))
    sale_price: Mapped[Decimal | None] = mapped_column(
        Numeric(12, 2), nullable=True
    )
    description: Mapped[str | None] = mapped_column(
        String(500), nullable=True
    )
    is_available: Mapped[bool] = mapped_column(
        Boolean, default=True
    )
    specs: Mapped[dict[str, object] | None] = mapped_column(
        JSON, nullable=True
    )

Тип внутри Mapped[...] описывает Python-значение атрибута. mapped_column() задаёт свойства столбца базы данных.

Модель ORM и схема Pydantic — не одно и то же

ORM-модель Pydantic-схема
описывает таблицу и хранение описывает входной или выходной HTTP-контракт
участвует в Session валидирует и сериализует данные
может содержать внутренние поля показывает клиенту только разрешённые поля

Не возвращаем таблицу «как есть» без публичной схемы: позже в модели могут появиться себестоимость, внутренний код поставщика или служебные флаги.

Создаём Engine

app/database.py

from sqlalchemy import Engine, create_engine


def create_database_engine(database_url: str) -> Engine:
    options = {}
    if database_url.startswith("sqlite"):
        options["connect_args"] = {"check_same_thread": False}

    return create_engine(database_url, **options)

FastAPI может выполнять синхронные endpoints в разных worker threads. Для учебного SQLite отключаем проверку, запрещающую использовать одно соединение за пределами создавшего его потока. Это не делает Session потокобезопасной.

Фабрика сессий

app/database.py

from sqlalchemy import Engine
from sqlalchemy.orm import Session, sessionmaker


def create_session_factory(
    engine: Engine,
) -> sessionmaker[Session]:
    return sessionmaker(
        bind=engine,
        class_=Session,
        autoflush=False,
        expire_on_commit=False,
    )
  • autoflush=False делает промежуточную отправку изменений более явной.
  • expire_on_commit=False оставляет уже загруженные значения доступными после commit.
  • Фабрика создаёт новые Session; она сама не является Session.

Инициализируем базу в lifespan

app/lifespan.py

from collections.abc import AsyncIterator
from contextlib import asynccontextmanager

from fastapi import FastAPI

from app.database import (
    create_database_engine,
    create_session_factory,
)
from app.models import Base


@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[None]:
    engine = create_database_engine(
        app.state.settings.database_url
    )
    Base.metadata.create_all(bind=engine)

    app.state.engine = engine
    app.state.session_factory = create_session_factory(engine)

    # Инициализация UserStorage из лекции 5 остаётся здесь
    yield

    engine.dispose()

Engine создаётся один раз при старте, а dispose() освобождает соединения при остановке приложения.

create_all() — не система миграций

Base.metadata.create_all() Alembic
создаёт отсутствующие таблицы хранит последовательность версий схемы
удобен для первого учебного запуска подходит для управляемых изменений окружений
не преобразует существующую таблицу под новую модель может добавлять, изменять и откатывать миграции

В следующей лекции уберём создание схемы из startup и передадим управление Alembic.

Передаём настройки в приложение

Lifespan получает тот же объект Settings, который использовался при сборке приложения. Это особенно важно для тестовой базы.

Dependency с Session

app/dependencies.py

from collections.abc import Iterator
from typing import Annotated

from fastapi import Depends, Request
from sqlalchemy.orm import Session


def get_session(request: Request) -> Iterator[Session]:
    session_factory = request.app.state.session_factory
    with session_factory() as session:
        yield session


SessionDep = Annotated[Session, Depends(get_session)]

Код до yield создаёт Session, значение передаётся endpoint, а выход из with гарантированно закрывает её.

Session и соединение — разные вещи

Создание Session не обязательно сразу берёт соединение из пула. Оно понадобится, когда Session впервые выполнит SQL или начнёт сохранять изменения.

get_session()
    ↓
Session создана
    ↓ первый SQL
соединение взято из Engine pool
    ↓ commit / rollback / close
соединение возвращено в pool

Поэтому Engine можно разделять между запросами, а Session — нельзя.

Получаем список товаров

app/routers/products.py

from sqlalchemy import select

from app.dependencies import SessionDep
from app.models import Product


@router.get("", response_model=list[ProductRead])
def list_products(session: SessionDep):
    statement = select(Product).order_by(Product.id)
    return session.scalars(statement).all()

select(Product) строит объект SQL-выражения. session.scalars() выполняет его и возвращает ORM-объекты без обёртки Row.

Фильтрация и сортировка

statement = (
    select(Product)
    .where(Product.category == category)
    .where(Product.is_available.is_(True))
    .order_by(Product.price, Product.id)
)
products = session.scalars(statement).all()

SQLAlchemy передаёт значения как связанные параметры. Не собирайте SQL из пользовательских строк через f-string: это создаёт риск SQL injection.

Получаем товар по первичному ключу

app/dependencies.py

from fastapi import HTTPException, Path, status

from app.models import Product


def get_product_or_404(
    product_id: Annotated[int, Path(ge=1)],
    session: SessionDep,
) -> Product:
    product = session.get(Product, product_id)
    if product is None:
        raise HTTPException(
            status_code=status.HTTP_404_NOT_FOUND,
            detail="Товар не найден",
        )
    return product


ProductDep = Annotated[Product, Depends(get_product_or_404)]

Session.get() предназначен для поиска по primary key и может использовать identity map текущей Session.

Создаём товар

app/routers/products.py

@router.post(
    "",
    response_model=ProductRead,
    status_code=status.HTTP_201_CREATED,
)
def create_product(
    product_data: ProductCreate,
    session: SessionDep,
    _admin: AdminUserDep,
):
    product = Product(
        **product_data.model_dump(mode="json")
    )
    session.add(product)
    session.commit()
    session.refresh(product)
    return product
  1. Схема Pydantic проверяет входной JSON.
  2. Создаётся новый ORM-объект.
  3. add() переводит объект в pending-состояние.
  4. commit() выполняет INSERT и фиксирует транзакцию.
  5. refresh() повторно читает значения, назначенные базой.

flush и commit

Операция Что делает
flush() отправляет pending-изменения в БД внутри текущей транзакции
commit() сначала выполняет flush, затем фиксирует транзакцию
rollback() отменяет незакоммиченные изменения текущей транзакции
refresh(obj) немедленно перечитывает состояние объекта из БД

flush() полезен, когда ID нового объекта нужен до финального commit, но сам по себе не делает изменение постоянным.

Обновляем товар

@router.patch(
    "/{product_id}",
    response_model=ProductRead,
)
def update_product(
    product: ProductDep,
    product_data: ProductUpdate,
    session: SessionDep,
    _admin: AdminUserDep,
):
    current = ProductRead.model_validate(product).model_dump(
        exclude={"id"}
    )
    patch = product_data.model_dump(exclude_unset=True)
    validated = ProductCreate.model_validate(current | patch)

    for field, value in validated.model_dump(mode="json").items():
        setattr(product, field, value)

    session.commit()
    session.refresh(product)
    return product

Сохраняем правило из лекции 3: после слияния PATCH повторно валидируем полное состояние, а не только присланные поля.

Удаляем товар

@router.delete(
    "/{product_id}",
    status_code=status.HTTP_204_NO_CONTENT,
)
def delete_product(
    product: ProductDep,
    session: SessionDep,
    _admin: AdminUserDep,
):
    session.delete(product)
    session.commit()
    return None

delete() только помечает ORM-объект. SQL DELETE отправляется во время flush, который вызывается внутри commit.

Что происходит в запросе записи

Шаг Компонент
1 FastAPI валидирует HTTP-вход через Pydantic
2 get_session создаёт Session для запроса
3 зависимости проверяют JWT, роль и существование товара
4 endpoint меняет ORM-объект и вызывает commit
5 Pydantic сериализует ORM-объект по ProductRead
6 dependency закрывает Session

Ошибки транзакции

from sqlalchemy.exc import IntegrityError


try:
    session.add(product)
    session.commit()
except IntegrityError:
    session.rollback()
    raise HTTPException(
        status_code=status.HTTP_409_CONFLICT,
        detail="Конфликт данных",
    )

После неудачного flush SQLAlchemy требует явный rollback(), прежде чем Session можно будет использовать снова. Не превращайте любую внутреннюю ошибку в 409: ловите только ожидаемые ограничения.

Транзакционная граница

Один endpoint может менять несколько таблиц. Коммитить после каждого маленького действия опасно: получится частично выполненная бизнес-операция.

with session.begin():
    reserve_stock(session, product_id, quantity)
    create_order(session, user_id, product_id, quantity)

Если второе действие завершится ошибкой, контекст транзакции откатит и резерв. В простом CRUD мы вызываем commit явно, а составные операции удобно обрамлять session.begin().

Синхронная или асинхронная SQLAlchemy

Синхронный стек Асинхронный стек
create_engine, Session create_async_engine, AsyncSession
psycopg в sync-режиме psycopg async или asyncpg
endpoint обычно объявлен через def endpoint объявлен через async def и использует await

async def не превращает синхронный драйвер в асинхронный. В этой лекции используем цельный sync-стек; FastAPI выполнит обычный def endpoint в thread pool.

SQLite для обучения, PostgreSQL для сервиса

SQLite PostgreSQL
один файл, нулевая настройка отдельный сервер и полноценная конкурентность
удобна для локальной практики и тестов типичный выбор для production API
ограниченная модель параллельной записи роли, схемы, развитые типы и инструменты эксплуатации

ORM уменьшает различия, но не стирает их полностью. SQL, типы, блокировки и производительность всё равно зависят от конкретной СУБД.

Что насчёт Django

Django обычно использует собственную встроенную Django ORM, а FastAPI не навязывает слой данных и часто работает с SQLAlchemy.

FastAPI + SQLAlchemy Django ORM
Engine и Session настраиваются явно соединения и QuerySet интегрированы во framework
модели наследуются от DeclarativeBase модели наследуются от django.db.models.Model
миграции выполняет Alembic миграции встроены в Django

Подключать SQLAlchemy к Django технически можно, но это не стандартный путь. В нашем FastAPI-проекте продолжаем с SQLAlchemy.

Почему не используем общую dev-базу в тестах

  • тест может удалить или испортить данные разработчика.
  • результат начнёт зависеть от содержимого файла на конкретной машине.
  • параллельные тесты будут конфликтовать.
  • порядок запуска снова станет значимым.

Изолированная база должна создаваться автоматически и удаляться вместе с временным каталогом pytest.

ORM-модели и Pydantic-схемы лежат отдельно. database.py отвечает за инфраструктуру подключения, а dependency — за срок жизни Session.

Минимальный checklist

  • использовать SQLAlchemy 2.0-style: select() и Session.scalars().
  • не создавать глобальную Session.
  • закрывать Session через dependency с yield.
  • коммитить на границе логической операции.
  • вызывать rollback после ожидаемой ошибки flush.
  • не смешивать ORM-модели с публичными Pydantic-схемами.
  • не использовать create_all() как замену миграциям.
  • запускать тесты на отдельной базе.
