Лекция 11: Redis в FastAPI — кэш, TTL и rate limiting

В прошлой лекции мы добавили MongoDB для гибких характеристик товара. Теперь подключим Redis для данных с коротким жизненным циклом: кэша, счётчиков и простого ограничения частоты запросов.

В Products API кэшируем чтение списка товаров и деталки, инвалидируем кэш после изменений и добавляем rate limit на логин. PostgreSQL остаётся источником истины, Redis помогает быстрее отвечать и защищать API от лишней нагрузки.

Что такое кэширование и зачем оно нужно?

Кэширование — это сохранение результата дорогой операции в быстром временном хранилище, чтобы не выполнять эту операцию заново при каждом одинаковом запросе.

  • API отвечает быстрее, потому что часть данных читается из RAM;
  • PostgreSQL получает меньше повторяющихся SELECT-запросов;
  • внешние API и тяжёлые вычисления можно вызывать реже;
  • пользователь чаще видит быстрый ответ, даже если основная база нагружена.

Цена кэша — риск устаревших данных. Поэтому вместе с кэшем всегда обсуждают TTL, ключи и инвалидацию.

Где Redis подходит проекту

Задача Почему Redis Что сделаем
частое чтение товаров ключ читается из RAM за миллисекунды кэш для GET /products и GET /products/{id}
устаревание данных у ключей есть TTL кэш сам исчезает через короткое время
инвалидация после записи ключи можно удалить явно очищаем кэш после POST, PUT, PATCH, DELETE
ограничение логина INCR атомарен счётчик попыток на IP с TTL

Redis не заменяет PostgreSQL и MongoDB. Он хранит производные данные, которые можно пересоздать, если кэш пропал.

Redis умеет не только кэш

Сценарий Как используется Где пригодится
кэш GET, SETEX, TTL быстрые ответы на повторяющиеся GET-запросы
rate limiting INCR + EXPIRE ограничение логина, API quota, защита дорогих endpoint
session storage session id как ключ, данные пользователя как значение серверные сессии, revoke-list, refresh-token state
backend для очередей Redis как broker/result backend для Celery или RQ фоновые задачи: email, отчёты, обработка файлов
pub/sub и streams каналы или Redis Streams уведомления, простая передача событий, realtime-сценарии
distributed locks ключ-блокировка с TTL не запускать одну тяжёлую задачу параллельно

В этой лекции берём кэш и rate limiting. Redis как backend для очередей вернётся в блоке про Celery: он удобен для старта, но для сложной маршрутизации и надёжной доставки часто выбирают RabbitMQ.

Кэш — не источник истины

flowchart LR API["FastAPI"] --> REDIS[("Redis
быстро, временно")] API --> PG[("PostgreSQL
источник истины")] API --> MDB[("MongoDB
характеристики")] REDIS -. "можно очистить" .-> API PG --> API MDB --> API

Если Redis пустой, приложение должно продолжить работать: прочитать данные из PostgreSQL, собрать ответ и снова положить его в кэш.

Cache-aside

  1. API строит ключ по параметрам запроса.
  2. Пробует прочитать JSON из Redis.
  3. Если ключ найден, возвращает ответ без SQL-запроса.
  4. Если ключа нет, читает PostgreSQL, сериализует ответ и кладёт его в Redis с TTL.
flowchart LR A["GET /products"] --> B{"ключ есть в Redis?"} B -- "cache hit" --> C["вернуть JSON из Redis"] B -- "cache miss" --> D["SELECT из PostgreSQL"] D --> E["сериализовать ответ"] E --> F["SETEX key ttl json"] F --> G["вернуть ответ"]

Этот паттерн простой и честный: кэш используется только на чтении, а запись остаётся обычной транзакционной операцией в основной базе.

TTL и инвалидация

Механизм Что делает Когда нужен
TTL Redis автоматически удаляет ключ через N секунд данные можно ненадолго устаревать
явный delete приложение удаляет конкретный ключ после изменения данных после PUT, PATCH, DELETE
namespace version ключи получают новую версию вместо массового удаления когда ключей слишком много

На лекции используем TTL плюс явную инвалидацию. Это достаточно понятно и хорошо подходит размеру учебного проекта.

Async Redis для async products

SQLAlchemy в проекте пока синхронная. Её запросы запускаем через run_in_threadpool(), а Redis вызываем напрямую через await. Так синхронный SQL-запрос и сетевой вызов Redis не блокируют event loop.

Операция Как выполняем
Синхронная SQLAlchemy await run_in_threadpool(query_products, ...)
Redis внутри async def from redis.asyncio import Redis

Это промежуточная архитектура: роутеры уже асинхронные, а полный переход PostgreSQL на AsyncSession можно сделать отдельно.

Один Redis-клиент на lifespan

app/lifespan.py

from redis.asyncio import Redis


@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[None]:
    settings = app.state.settings
    engine = create_database_engine(settings.database_url)
    app.state.engine = engine
    app.state.session_factory = create_session_factory(engine)

    redis_client: Redis | None = None
    app.state.redis = None

    try:
        if settings.redis_url is not None:
            redis_client = Redis.from_url(
                settings.redis_url,
                decode_responses=True,
            )
            await redis_client.ping()
            app.state.redis = redis_client

        # здесь остаётся существующий bootstrap admin и MongoDB
        yield
    finally:
        if redis_client is not None:
            await redis_client.aclose()
        engine.dispose()

decode_responses=True возвращает строки вместо bytes. Это удобно для JSON-кэша и счётчиков.

Dependency для Redis

app/dependencies.py

from redis.asyncio import Redis


def get_redis(request: Request) -> Redis | None:
    return request.app.state.redis


RedisDep = Annotated[Redis | None, Depends(get_redis)]

При redis is None кэш и limiter пропускаются: API продолжает работать через PostgreSQL. Это graceful degradation, но без Redis временно исчезает и защита логина.

Ключи должны быть предсказуемыми

product:detail:42
products:list:v3:search=phone:limit=10:category=electronics:available=True
auth:login:192.168.1.20
  • ключ должен включать все параметры, которые влияют на ответ;
  • одинаковые запросы должны давать одинаковый ключ;
  • у разных endpoint не должно быть случайных пересечений;
  • не кладём в ключи пароли, JWT и другие секреты.

Ключ — часть API-контракта внутри приложения. Если забыть параметр, Redis начнёт отдавать ответ от другого запроса.

Сервис кэша товаров

app/cache.py

from __future__ import annotations

import json
from typing import Any

from redis.asyncio import Redis


PRODUCT_LIST_VERSION_KEY = "products:list:version"


async def get_product_list_version(redis: Redis) -> int:
    version = await redis.get(PRODUCT_LIST_VERSION_KEY)
    if version is None:
        return 0
    return int(version)


async def make_product_list_cache_key(
    redis: Redis,
    *,
    search: str | None,
    limit: int,
    category_slug: str | None,
    only_available: bool,
) -> str:
    version = await get_product_list_version(redis)
    return (
        f"products:list:v{version}:"
        f"search={search or ''}:"
        f"limit={limit}:"
        f"category={category_slug or ''}:"
        f"available={only_available}"
    )


def make_product_detail_cache_key(product_id: int) -> str:
    return f"product:detail:{product_id}"

Начинаем с v0: первая запись увеличит версию до v1, поэтому даже закэшированный пустой список сразу перестанет использоваться. Версия позволяет не удалять много list-ключей по шаблону.

JSON helpers

app/cache.py

async def get_json(redis: Redis, key: str) -> Any | None:
    value = await redis.get(key)
    if value is None:
        return None
    return json.loads(value)


async def set_json(
    redis: Redis,
    key: str,
    value: Any,
    *,
    ttl_seconds: int,
) -> None:
    await redis.setex(
        key,
        ttl_seconds,
        json.dumps(value, ensure_ascii=False),
    )


async def invalidate_product_cache(
    redis: Redis | None,
    *,
    product_id: int | None = None,
) -> None:
    if redis is None:
        return
    await redis.incr(PRODUCT_LIST_VERSION_KEY)
    if product_id is not None:
        await redis.delete(make_product_detail_cache_key(product_id))

Кэшируем не ORM-объекты, а уже готовый JSON-совместимый ответ. Так Redis не зависит от внутреннего состояния SQLAlchemy-сессии.

Sync helpers для чтения из PostgreSQL

app/routers/products.py

from sqlalchemy.orm import Session


def query_products(
    session: Session,
    *,
    search: str | None,
    limit: int,
    category_slug: str | None,
    only_available: bool,
) -> list[ProductRead]:
    statement = (
        select(Product)
        .join(Product.category)
        .options(selectinload(Product.category))
        .order_by(Category.name, Product.title)
    )
    if search:
        statement = statement.where(
            Product.title.ilike(f"%{search}%")
        )
    statement = statement.where(
        Product.is_available == only_available
    )
    if category_slug:
        statement = statement.where(
            Category.slug == category_slug
        )

    products = session.scalars(statement.limit(limit)).all()
    return [
        ProductRead.model_validate(product)
        for product in products
    ]


def read_product_from_db(
    session: Session,
    product_id: int,
) -> ProductRead:
    product = get_product_or_404(product_id, session)
    return ProductRead.model_validate(product)

Эти функции остаются синхронными и ничего не знают о Redis. Async-endpoint запускает их в thread pool и получает уже готовые Pydantic-модели.

Кэшируем список товаров

app/routers/products.py

from app.cache import (
    get_json,
    invalidate_product_cache,
    make_product_detail_cache_key,
    make_product_list_cache_key,
    set_json,
)
from app.dependencies import RedisDep, SettingsDep
from fastapi import Path
from fastapi.concurrency import run_in_threadpool


@router.get("", response_model=list[ProductRead])
async def list_products(
    session: SessionDep,
    redis: RedisDep,
    settings: SettingsDep,
    search: SearchParam = None,
    limit: LimitParam = 10,
    category_slug: CategorySlugParam = None,
    only_available: bool = True,
) -> list[ProductRead]:
    cache_key = None
    if redis is not None:
        cache_key = await make_product_list_cache_key(
            redis,
            search=search,
            limit=limit,
            category_slug=category_slug,
            only_available=only_available,
        )
        cached = await get_json(redis, cache_key)
        if cached is not None:
            return [ProductRead.model_validate(item) for item in cached]

    response = await run_in_threadpool(
        query_products,
        session,
        search=search,
        limit=limit,
        category_slug=category_slug,
        only_available=only_available,
    )
    if redis is not None and cache_key is not None:
        await set_json(
            redis,
            cache_key,
            [item.model_dump(mode="json") for item in response],
            ttl_seconds=settings.product_cache_ttl_seconds,
        )
    return response

query_products() остаётся обычной функцией и возвращает готовые ProductRead. Thread pool не делает SQLAlchemy асинхронной, но не даёт ей блокировать event loop.

Кэшируем деталку

@router.get("/{product_id}", response_model=ProductRead)

Кэш деталки проще, чем кэш списка: ключ зависит только от product_id.

Sync helpers для записи в PostgreSQL

app/routers/products.py

def create_product_in_db(
    session: Session,
    product_data: ProductCreate,
) -> ProductRead:
    category = get_category_or_404(
        product_data.category_id,
        session,
    )
    product = Product(
        **product_data.model_dump(
            mode="json",
            exclude={"category_id"},
        ),
        category=category,
    )
    session.add(product)
    session.commit()
    return ProductRead.model_validate(
        get_product_or_404(product.id, session)
    )


def replace_product_in_db(
    session: Session,
    product: Product,
    product_data: ProductCreate,
) -> ProductRead:
    category = get_category_or_404(
        product_data.category_id,
        session,
    )
    for field, value in product_data.model_dump(
        mode="json",
        exclude={"category_id"},
    ).items():
        setattr(product, field, value)
    product.category = category
    session.commit()
    return ProductRead.model_validate(
        get_product_or_404(product.id, session)
    )


def update_product_in_db(
    session: Session,
    product: Product,
    product_data: ProductUpdate,
) -> ProductRead:
    current = ProductCreate.model_validate(product).model_dump()
    patch = product_data.model_dump(exclude_unset=True)
    validated = ProductCreate.model_validate(current | patch)
    return replace_product_in_db(session, product, validated)


def delete_product_from_db(
    session: Session,
    product: Product,
) -> None:
    session.delete(product)
    session.commit()

Commit выполняется внутри sync-helper. Инвалидацию вызываем только после того, как helper успешно завершился.

Инвалидация после POST и PUT

@router.post(
    "",
    response_model=ProductRead,
    status_code=HTTP_201_CREATED,
)
async def create_product(
    product_data: ProductCreate,
    session: SessionDep,
    redis: RedisDep,
    _admin: AdminRoleDep,

    response = await run_in_threadpool(
        create_product_in_db,
        session,
        product_data,
    )
    await invalidate_product_cache(redis)
    return response


@router.put("/{product_id}", response_model=ProductRead)
async def replace_product(
    product: ProductDep,
    product_data: ProductCreate,
    session: SessionDep,
    redis: RedisDep,
    _admin: AdminRoleDep,
) -> ProductRead:
    response = await run_in_threadpool(

POST увеличивает только версию списков. PUT меняет существующий товар, поэтому дополнительно удаляет его detail-key.

Инвалидация после PATCH и DELETE

@router.patch("/{product_id}", response_model=ProductRead)

    product: ProductDep,
    product_data: ProductUpdate,
    session: SessionDep,

    _admin: AdminRoleDep,

@router.delete(
    "/{product_id}",
    status_code=HTTP_204_NO_CONTENT,
)
async def delete_product(
    product: ProductDep,
    session: SessionDep,
    redis: RedisDep,
    _admin: AdminRoleDep,
) -> None:
    product_id = product.id
    await run_in_threadpool(
        delete_product_from_db,
        session,
        product,
    )
    await invalidate_product_cache(redis, product_id=product_id)

Кэш удаляем только после успешного commit(). Если транзакция упала, старый кэш остаётся соответствующим старым данным.

Что инвалидировать

Операция Кэш деталки Кэш списков
POST product нет старой деталки INCR products:list:version
PUT/PATCH product DELETE product:detail:{id} INCR products:list:version
DELETE product DELETE product:detail:{id} INCR products:list:version

В текущем проекте категория не редактируется. Если позже появится PUT/PATCH категории, он тоже должен инвалидировать product-кэш: категория входит в ProductRead и влияет на фильтры списков.

Rate limiting через INCR

Redis хорош для счётчиков, потому что INCR выполняется атомарно. Даже если два запроса пришли одновременно, счётчик не потеряет одно из увеличений.

auth:login:203.0.113.10 = 1, TTL 60 секунд
auth:login:203.0.113.10 = 2
auth:login:203.0.113.10 = 3
...
после лимита отвечаем 429 Too Many Requests

Это простой fixed window limiter. Он не идеален на границе минуты, но отлично подходит для первой реализации.

Dependency rate limit

app/dependencies.py

from starlette.status import HTTP_429_TOO_MANY_REQUESTS


async def limit_login_attempts(
    request: Request,
    redis: RedisDep,
    settings: SettingsDep,
) -> None:
    if redis is None:
        return

    client_host = request.client.host if request.client else "unknown"
    key = f"auth:login:{client_host}"
    attempts = await redis.incr(key)
    if attempts == 1:
        await redis.expire(key, 60)

    if attempts > settings.auth_rate_limit_per_minute:
        raise HTTPException(
            status_code=HTTP_429_TOO_MANY_REQUESTS,
            detail="Too many login attempts",
        )


LoginRateLimitDep = Annotated[None, Depends(limit_login_attempts)]

В реальном сервисе IP за прокси надо брать аккуратно: только из доверенного заголовка, который выставляет ваш reverse proxy.

Подключаем лимит к логину

app/routers/auth.py

from app.dependencies import LoginRateLimitDep


@router.post("/token", response_model=Token)
def login(
    form_data: LoginForm,
    _rate_limit: LoginRateLimitDep,
    session: SessionDep,
    settings: SettingsDep,
) -> Token:
    try:
        user = authenticate_user(
            session,
            form_data.username,
            form_data.password,
        )
    except UnknownHashError:
        raise invalid_credentials()
    if user is None:
        raise invalid_credentials()

    token = create_access_token(str(user.id), settings)
    return Token(access_token=token)

Лимит срабатывает до проверки пароля. Это снижает стоимость brute force и не раскрывает, существует ли пользователь.

Тестирование

Что проверяем Как
генерация ключей unit-тесты без Redis
JSON helpers небольшой FakeRedis или реальный Redis
cache hit второй GET возвращает ответ из Redis
инвалидация после PATCH старый detail-key удалён
первый товар после пустого списка версия меняется с v0 на v1
rate limit после N запросов логин отвечает 429

Для учебной проверки достаточно поднять Redis в Compose и прогнать несколько интеграционных сценариев через TestClient.

Типичные ошибки

  • кэшировать ORM-объект вместо JSON-ответа;
  • забыть один query parameter в cache key;
  • инвалидировать кэш до commit();
  • делать KEYS products:* в production;
  • хранить в Redis секреты без необходимости;
  • считать Redis постоянным хранилищем для данных, которые нельзя потерять.

Самая частая проблема кэша не техническая, а смысловая: приложение начинает быстро отдавать неправильные данные.

Практика

  1. Добавить Redis в Compose и настройки приложения.
  2. Подключить redis.asyncio.Redis в существующий lifespan.
  3. Создать app/cache.py с ключами, JSON helpers и инвалидацией.
  4. Закэшировать список товаров и деталку товара.
  5. Инвалидировать кэш после POST, PUT, PATCH и DELETE.
  6. Добавить rate limit на POST /auth/token.
  7. Проверить cache hit, cache miss, invalidation и 429.

Дополнительно: сделать graceful degradation для кэша чтения, чтобы товары продолжали открываться при выключенном Redis.

Итоги

  • Redis хранит временные производные данные, а не заменяет PostgreSQL.
  • Cache-aside сначала проверяет Redis, а при miss читает основную базу.
  • TTL ограничивает жизнь кэша, явная инвалидация убирает устаревшие ответы после записи.
  • INCR и EXPIRE дают простой rate limiter.
  • Ключи кэша должны включать все параметры запроса.
  • Async products используют redis.asyncio.Redis, а sync SQLAlchemy временно запускается через thread pool.
