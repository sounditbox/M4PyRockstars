Лекция 4: Структура FastAPI-приложения, APIRouter и зависимости

В прошлой лекции мы вынесли Pydantic-схемы из main.py. Теперь продолжим рефакторинг: разделим эндпоинты, хранилище, зависимости и настройки, а также разберём жизненный цикл приложения.

Цель занятия — не построить «идеальную архитектуру», а научиться разделять ответственность так, чтобы проект можно было безопасно расширять.

Стартовая точка

project/
└── app/

Приложение работает, но main.py всё ещё знает слишком много и будет быстро расти.

Почему одного файла становится мало

Проблема Последствие
эндпоинты разных ресурсов перемешаны сложно найти и изменить нужный сценарий
хранилище — глобальный словарь рядом с HTTP-кодом логика хранения связана с транспортным слоем
настройки записаны константами секреты и окружения трудно менять безопасно
вспомогательные проверки копируются поведение разных эндпоинтов начинает расходиться
ресурсы создаются в случайных местах непонятно, где их открывать и закрывать

Модульность нужна не ради количества файлов, а чтобы у каждой части появилась понятная зона ответственности.

Что такое APIRouter

APIRouter — объект для группировки связанных path operations. По интерфейсу он похож на уменьшенный FastAPI: поддерживает декораторы get, post, patch, параметры, зависимости, ответы и теги.

from fastapi import APIRouter


router = APIRouter(
    prefix="/products",
    tags=["products"],
)


@router.get("")
def list_products():
    ...

Роутер сам по себе не запускает приложение. Его нужно подключить к экземпляру FastAPI.

Переносим Products API в роутер

app/routers/products.py

from fastapi import APIRouter, status

from app.schemas import ProductCreate, ProductRead, ProductUpdate


router = APIRouter(
    prefix="/products",
    tags=["products"],
)


@router.get("", response_model=list[ProductRead])
def list_products():
    ...


@router.post(
    "",
    response_model=ProductRead,
    status_code=status.HTTP_201_CREATED,
)
def create_product(product_data: ProductCreate):
    ...

Остальные GET, PUT, PATCH и DELETE переносятся по тому же принципу. URL и модели ответа не должны измениться.

Подключаем роутер к приложению

app/main.py

from fastapi import FastAPI

from app.routers import products


app = FastAPI(title="Products API")
app.include_router(products.router)

include_router() копирует path operations роутера в основное приложение при запуске. Это не отдельное подприложение и не дополнительный сетевой слой.

GET     /products
POST    /products
GET     /products/{product_id}
PUT     /products/{product_id}
PATCH   /products/{product_id}
DELETE  /products/{product_id}

Где задавать prefix, tags и зависимости

Место Когда использовать
APIRouter(...) настройка относится ко всем эндпоинтам ресурса
@router.get(...) настройка нужна только одной операции
app.include_router(...) приложение добавляет общий префикс версии API или переиспользует роутер 
app.include_router(
    products.router,
    prefix="/api/v1",
)

Итоговый путь складывается из префиксов: /api/v1 + /products + /{product_id}.

Хранилище — отдельная ответственность

app/storage.py

from app.schemas import ProductRead


class ProductStorage:
    def __init__(self) -> None:
        self.products: dict[int, ProductRead] = {}
        self.next_id = 1

    def get(self, product_id: int) -> ProductRead | None:
        return self.products.get(product_id)

    def list(self) -> list[ProductRead]:
        return list(self.products.values())

    def delete(self, product_id: int) -> None:
        del self.products[product_id]

    def clear(self) -> None:
        self.products.clear()
        self.next_id = 1

Это всё ещё in-memory-хранилище, а не production-репозиторий. Но HTTP-код больше не обязан знать, что данные лежат в словаре.

Что такое dependency injection

Dependency injection — подход, при котором функция объявляет, что ей нужно, а внешний механизм предоставляет готовое значение.

Без зависимости С зависимостью
эндпоинт сам создаёт или ищет объект эндпоинт получает готовый объект параметром
настройки и ресурсы привязаны к реализации реализацию можно централизованно заменить
проверки копируются общая проверка выполняется в одном месте

В FastAPI механизм DI построен вокруг Depends. Зависимостью может быть обычная или асинхронная функция, вызываемый объект или другая зависимость.

Depends и Annotated

from typing import Annotated

from fastapi import Depends


def get_storage() -> ProductStorage:
    return ProductStorage()


StorageDep = Annotated[
    ProductStorage,
    Depends(get_storage),
]


@router.get("")
def list_products(storage: StorageDep):
    return storage.list()

ProductStorage описывает тип значения, а Depends(get_storage) сообщает FastAPI, как это значение получить.

Пока это только форма записи

На следующем шаге исправим важную проблему примера: новая ProductStorage() не должна создаваться для каждого запроса.

Зависимость может зависеть от запроса

app/dependencies.py

from typing import Annotated

from fastapi import Depends, Request

from app.storage import ProductStorage


def get_product_storage(request: Request) -> ProductStorage:
    return request.app.state.product_storage


StorageDep = Annotated[
    ProductStorage,
    Depends(get_product_storage),
]

Request FastAPI передаёт автоматически. Через request.app зависимость получает текущее приложение и его ресурсы.

Переиспользуем поиск товара

app/dependencies.py

from fastapi import HTTPException, Path, status

from app.schemas import ProductRead


def get_product_or_404(
    product_id: Annotated[int, Path(ge=1)],
    storage: StorageDep,
) -> ProductRead:
    product = storage.get(product_id)
    if product is None:
        raise HTTPException(
            status_code=status.HTTP_404_NOT_FOUND,
            detail="Товар не найден",
        )
    return product


ProductDep = Annotated[
    ProductRead,
    Depends(get_product_or_404),
]

FastAPI сам передаст product_id из пути и сначала разрешит зависимость StorageDep.

Эндпоинт получает готовый ресурс

@router.get(
    "/{product_id}",
    response_model=ProductRead,
)
def get_product(product: ProductDep):
    return product


@router.delete(
    "/{product_id}",
    status_code=status.HTTP_204_NO_CONTENT,
)
def delete_product(
    product: ProductDep,
    storage: StorageDep,
):
    storage.delete(product.id)
    return None

Если товара нет, выполнение эндпоинта не начнётся: зависимость сразу вернёт 404. Если товар найден, функция работает с готовой моделью.

Граф зависимостей и кэш запроса

delete_product
├── ProductDep
│   ├── product_id
│   └── StorageDep
└── StorageDep

FastAPI строит граф, разрешает зависимости в нужном порядке и по умолчанию вызывает одинаковую зависимость только один раз за запрос.

Настройка Поведение
Depends(get_storage) результат переиспользуется внутри текущего запроса
Depends(get_storage, use_cache=False) зависимость вызывается повторно при каждом использовании

Кэш зависимости живёт только во время одного запроса. Это не замена Redis, lru_cache или кэшу приложения.

Где можно подключать зависимости

Уровень Пример Когда подходит
параметр функции storage: StorageDep эндпоинту нужен результат зависимости
декоратор операции @router.post(..., dependencies=[Depends(check)]) проверку нужно выполнить, но её результат не используется
APIRouter APIRouter(dependencies=[...]) правило относится ко всему ресурсу
FastAPI FastAPI(dependencies=[...]) правило действительно для всего приложения

На следующей лекции этот механизм позволит защищать весь роутер аутентификацией без копирования проверки токена.

Зависимости с yield

def get_resource():
    resource = open_resource()
    try:
        yield resource
    finally:
        resource.close()
Часть функции Когда выполняется
код до yield до запуска эндпоинта
значение после yield передаётся эндпоинту как результат зависимости
блок finally после обработки запроса, даже если возникло исключение

Главный будущий пример — сессия базы данных. Открывать и закрывать её вручную в каждом эндпоинте не потребуется.

Жизненный цикл приложения

Lifespan управляет ресурсами, которые создаются один раз при запуске процесса приложения и освобождаются при его остановке.

from collections.abc import AsyncIterator
from contextlib import asynccontextmanager

from fastapi import FastAPI

from app.storage import ProductStorage


@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[None]:
    app.state.product_storage = ProductStorage()

    yield

    app.state.product_storage.clear()

Код до yield выполняется при старте, после yield — при корректном завершении приложения.

yield-зависимость или lifespan

Вопрос Зависимость с yield Lifespan
частота для каждого запроса один раз на процесс приложения
типичный ресурс сессия БД, транзакция, временный файл пул соединений, HTTP-клиент, ML-модель
как получить в эндпоинте через Depends обычно через зависимость, читающую app.state

В нашем примере ProductStorage существует всё время работы приложения, а get_product_storage выдаёт ссылку на него конкретному запросу.

Настройки приложения

Настройки — значения, которые меняются между окружениями или не должны быть записаны в исходном коде:

  • название приложения и режим отладки.
  • URL базы данных и внешних сервисов.
  • секреты подписи токенов.
  • таймауты, лимиты и флаги функций.

Переменные окружения всегда приходят как строки. pydantic-settings преобразует и валидирует их по типизированной модели.

uv add pydantic-settings

Настройки как зависимость

app/dependencies.py

from functools import lru_cache
from typing import Annotated

from fastapi import Depends

from app.core.config import Settings


@lru_cache
def get_settings() -> Settings:
    return Settings()


SettingsDep = Annotated[
    Settings,
    Depends(get_settings),
]

lru_cache создаёт Settings только при первом вызове, поэтому файл .env не читается для каждого запроса.

В тестах зависимость можно заменить через app.dependency_overrides, а кэш — очистить вызовом get_settings.cache_clear().

Фабрика приложения

app/main.py

from fastapi import FastAPI

from app.core.config import Settings
from app.dependencies import get_settings
from app.lifespan import lifespan
from app.routers import products


def create_app(settings: Settings | None = None) -> FastAPI:
    settings = settings or get_settings()

    application = FastAPI(
        title=settings.app_name,
        debug=settings.debug,
        lifespan=lifespan,
    )
    application.include_router(
        products.router,
        prefix=settings.api_prefix,
    )
    return application


app = create_app()

В дереве проекта появляется app/lifespan.py. Фабрика не обязательна для каждого маленького API, но здесь она делает точку сборки явной.

После переноса точки входа сервер запускается из корня проекта:

uv run fastapi dev app/main.py

Так .env также ищется относительно корня, из которого запускается команда.

Как собирается запрос

Шаг Что происходит
1 create_app() читает настройки и создаёт FastAPI
2 lifespan создаёт ProductStorage в app.state
3 include_router() подключает Products API с префиксом версии
4 FastAPI строит граф зависимостей для входящего запроса
5 зависимости получают хранилище и находят товар либо возвращают 404
6 эндпоинт выполняет действие и сериализует ответ по Pydantic-схеме

Практика

Задача: разделить готовый Products API на модули, не изменив его поведение для клиента.

  1. Создайте пакеты app/routers и app/core с файлами __init__.py.
  2. Перенесите CRUD-эндпоинты в app/routers/products.py и подключите роутер через include_router().
  3. Перенесите in-memory-хранилище в класс ProductStorage внутри app/storage.py.
  4. Создайте lifespan, который помещает одно хранилище в app.state.
  5. Добавьте StorageDep и ProductDep, затем уберите повторяющуюся проверку 404 из эндпоинтов.
  6. Добавьте Settings, файлы .env/.env.example и зависимость get_settings().
  7. Соберите приложение в create_app() и добавьте общий префикс /api/v1.
  8. Проверьте в Swagger UI полный CRUD, ошибки 404/422 и итоговые URL.

Дополнительная задача: добавьте зависимость, которая читает заголовок X-Request-ID, и подключите её ко всему Products-роутеру.
