Лекция 9: Связи таблиц в SQLAlchemy — ForeignKey, relationship и N+1

В прошлой лекции мы подключили проект к PostgreSQL через psycopg и передали изменение схемы базы Alembic-миграциям. Теперь сделаем следующий шаг: перестанем хранить категорию товара строкой внутри products и вынесем категории в отдельную таблицу.

На этой лекции разберём связи между таблицами, перенесём существующие категории и научимся загружать связанные объекты без проблемы N+1.

Связь 1-to-n и n-to-1

Категория (1) ───────── Товары (n)

1-to-n: одна категория содержит много товаров
n-to-1: много товаров ссылаются на одну категорию

ForeignKey хранит связь в PostgreSQL: products.category_id → categories.id. Он находится на стороне n и не позволяет сослаться на несуществующую категорию.

relationship() даёт удобные Python-атрибуты для той же связи: product.category в направлении n-to-1 и category.products в направлении 1-to-n.

Обновляем ORM-модели

app/models.py

from __future__ import annotations

from decimal import Decimal

from sqlalchemy import (
    Boolean,
    CheckConstraint,
    ForeignKey,
    Integer,
    JSON,
    Numeric,
    String,
)
from sqlalchemy.orm import Mapped, mapped_column, relationship


class Category(Base):
    __tablename__ = "categories"

    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(
        String(80), unique=True, index=True
    )
    slug: Mapped[str] = mapped_column(
        String(40), unique=True, index=True
    )

    products: Mapped[list[Product]] = relationship(
        back_populates="category"
    )


class Product(Base):
    __tablename__ = "products"

    id: Mapped[int] = mapped_column(primary_key=True)
    title: Mapped[str] = mapped_column(String(80), index=True)
    category_id: Mapped[int] = mapped_column(
        ForeignKey("categories.id"),
        index=True,
    )
    price: Mapped[Decimal] = mapped_column(Numeric(12, 2))
    sale_price: Mapped[Decimal | None] = mapped_column(
        Numeric(12, 2), nullable=True
    )
    description: Mapped[str | None] = mapped_column(
        String(500), nullable=True
    )
    is_available: Mapped[bool] = mapped_column(
        Boolean, default=True
    )
    stock_count: Mapped[int] = mapped_column(
        Integer,
        CheckConstraint(
            "stock_count >= 0",
            name="ck_products_stock_count_nonnegative",
        ),
        default=0,
        server_default="0",
    )
    specs: Mapped[dict[str, object] | None] = mapped_column(
        JSON, nullable=True
    )

    category: Mapped[Category] = relationship(
        back_populates="products"
    )

from __future__ import annotations позволяет ссылаться на Product и Category в типах до того, как оба класса полностью объявлены.

Что значит back_populates

Category.products  ◄──── back_populates ────►  Product.category

back_populates связывает две стороны одного отношения. SQLAlchemy понимает, что если product.category = category, то этот товар относится к коллекции category.products.

category = Category(name="Electronics", slug="electronics")
product = Product(title="Keyboard", price=120, category=category)

assert product.category is category
assert product in category.products

Это синхронизация ORM-объектов в памяти. Финальная проверка целостности всё равно происходит в базе через ForeignKey.

Миграция с существующими данными

Сначала доводим PostgreSQL-базу до текущего head, затем создаём следующую ревизию поверх уже существующей цепочки миграций:

alembic upgrade head
alembic revision --autogenerate -m "create product categories"

1. Создать таблицу categories
2. Добавить products.category_id как nullable
3. Перенести уникальные строки products.category в categories
4. Заполнить products.category_id
5. Сделать category_id NOT NULL
6. Удалить старую колонку products.category

Это не просто изменение схемы, а data migration: миграция должна переложить уже существующие данные в новую форму.

Что такое backfill

Backfill — это заполнение нового поля данными из старого формата. Он нужен, потому что в PostgreSQL уже есть товары со строковой категорией.

Было:
products.category = "electronics"

Стало:
categories: id=1, name="Electronics", slug="electronics"
products.category_id = 1
  1. Берём уникальные значения из products.category.
  2. Создаём по ним строки в categories.
  3. Записываем полученные ID в products.category_id.

После backfill можно безопасно включить NOT NULL и удалить старую строковую колонку.

Код backfill

alembic/versions/xxxx_create_product_categories.py

products_table = sa.table(
    "products",
    sa.column("category", sa.String),
    sa.column("category_id", sa.Integer),
)
categories_table = sa.table(
    "categories",
    sa.column("id", sa.Integer),
    sa.column("name", sa.String),
    sa.column("slug", sa.String),
)


def slugify_category(name: str) -> str:
    return name.strip().lower().replace(" ", "-")


def backfill_categories() -> None:
    connection = op.get_bind()

    category_names = connection.execute(
        sa.select(products_table.c.category).distinct()
    ).scalars()

    category_ids: dict[str, int] = {}

    for name in sorted(category_names):
        category_id = connection.execute(
            categories_table.insert().values(
                name=name.title(),
                slug=slugify_category(name),
            ).returning(categories_table.c.id)
        ).scalar_one()
        category_ids[name] = category_id

    for name, category_id in category_ids.items():
        connection.execute(
            products_table.update()
            .where(products_table.c.category == name)
            .values(category_id=category_id)
        )

Функцию вызываем внутри upgrade(): после добавления nullable-поля category_id, но до включения NOT NULL. PostgreSQL сам генерирует ID, а RETURNING сразу отдаёт его для обновления товаров.

Завершаем миграцию в PostgreSQL

В начале upgrade() остаются созданные autogenerate операции op.create_table("categories", ...) и индексы категории. После них добавляем nullable-колонку и внешний ключ, переносим данные и только потом включаем NOT NULL.

op.add_column(
    "products",
    sa.Column("category_id", sa.Integer(), nullable=True),
)
op.create_index(
    op.f("ix_products_category_id"),
    "products",
    ["category_id"],
)
op.create_foreign_key(
    op.f("fk_products_category_id_categories"),
    "products",
    "categories",
    ["category_id"],
    ["id"],
)

backfill_categories()

op.alter_column(
    "products",
    "category_id",
    existing_type=sa.Integer(),
    nullable=False,
)
op.drop_column("products", "category")

После создания constraint PostgreSQL сам отклонит category_id, которого нет в categories. Дополнительная настройка соединения для проверки внешних ключей не нужна.

Downgrade тоже думает о данных

Откат должен вернуть строковую категорию в products.category до удаления category_id и таблицы categories.

downgrade:
1. Добавить products.category как nullable
2. Заполнить её из categories.slug или categories.name
3. Сделать products.category NOT NULL
4. Удалить foreign key и category_id
5. Удалить таблицу categories

Если downgrade теряет важные данные, это нужно явно понимать до релиза. Иногда откат схемы возможен, а откат смысла данных — нет.

    @field_validator("title")

from app.dependencies import SessionDep, get_category_or_404
from app.models import Category, Product
from app.schemas import CategoryCreate, CategoryRead
from app.security import AdminRoleDep


router = APIRouter(prefix="/categories", tags=["Categories"])


@router.post(
    "",
    response_model=CategoryRead,
    status_code=status.HTTP_201_CREATED,
)
def create_category(
    payload: CategoryCreate,
    session: SessionDep,
    _admin: AdminRoleDep,
) -> Category:
    category = Category(**payload.model_dump())
    session.add(category)

    try:
        session.commit()
    except IntegrityError as exc:
        session.rollback()
        raise HTTPException(
            status_code=status.HTTP_409_CONFLICT,
            detail="Категория с таким name или slug уже существует",

    session.refresh(category)
    return category

Создаём товар со связью

from app.dependencies import (
    ProductDep,
    SessionDep,
    get_category_or_404,
    get_product_or_404,
)


@router.post(
    "",
    response_model=ProductRead,
    status_code=status.HTTP_201_CREATED,
)
def create_product(
    product_data: ProductCreate,
    session: SessionDep,
    _admin: AdminRoleDep,
) -> Product:
    category = get_category_or_404(
        product_data.category_id,
        session,
    )

    product = Product(
        **product_data.model_dump(
            mode="json",
            exclude={"category_id"},
        ),
        category=category,
    )
    session.add(product)
    session.commit()

    return get_product_or_404(product.id, session)

Мы присваиваем ORM-объект category, а SQLAlchemy сам выставляет нужный category_id. Это удобнее и выразительнее, чем вручную синхронизировать оба поля.

Обновляем PUT товара

@router.put("/{product_id}", response_model=ProductRead)
def replace_product(
    product: ProductDep,
    product_data: ProductCreate,
    session: SessionDep,
    _admin: AdminRoleDep,
) -> Product:
    category = get_category_or_404(
        product_data.category_id,
        session,
    )

    for field, value in product_data.model_dump(
        mode="json",
        exclude={"category_id"},
    ).items():
        setattr(product, field, value)

    product.category = category
    session.commit()
    return get_product_or_404(product.id, session)

PUT получает полное состояние товара. Обычные поля обновляются как раньше, а категория назначается ORM-объектом.

Обновляем PATCH товара

@router.patch("/{product_id}", response_model=ProductRead)
def update_product(
    product: ProductDep,
    product_data: ProductUpdate,
    session: SessionDep,
    _admin: AdminRoleDep,
) -> Product:
    current = ProductCreate.model_validate(product).model_dump()
    patch = product_data.model_dump(exclude_unset=True)
    validated = ProductCreate.model_validate(current | patch)

    category = get_category_or_404(
        validated.category_id,
        session,
    )
    for field, value in validated.model_dump(
        mode="json",
        exclude={"category_id"},
    ).items():
        setattr(product, field, value)

    product.category = category
    session.commit()
    return get_product_or_404(product.id, session)

ProductCreate.model_validate(product) работает благодаря from_attributes=True и собирает текущее состояние вместе с category_id. Затем проект сохраняет прежнюю проверку полного объекта после частичного обновления.

Получаем товар с категорией

app/dependencies.py

from sqlalchemy import select
from sqlalchemy.orm import selectinload


def get_product_or_404(
    product_id: Annotated[int, Path(ge=1)],
    session: SessionDep,
) -> Product:
    statement = (
        select(Product)
        .options(selectinload(Product.category))
        .where(Product.id == product_id)
    )
    product = session.scalar(statement)
    if product is None:
        raise HTTPException(
            status_code=HTTP_404_NOT_FOUND,
            detail="Товар не найден",
        )
    return product

selectinload(Product.category) заранее загружает связанную категорию. Когда FastAPI сериализует ProductRead, поле category уже готово.

Что такое lazy loading

По умолчанию relationship() часто загружается лениво: связанный объект не читается из базы до первого обращения к атрибуту.

Проблема N+1

1 запрос: получить N товаров
до N запросов: получить ещё не загруженные категории при доступе

Итого в худшем случае: N + 1 SELECT

Identity map может переиспользовать уже загруженную категорию, поэтому реальное число запросов зависит от количества разных категорий. Но оно всё равно растёт вместе с данными и делает производительность плохо предсказуемой.

selectinload решает N+1

statement = (
    select(Product)
    .options(selectinload(Product.category))
    .order_by(Product.id)
)
products = list(session.scalars(statement))

SELECT ... FROM products ORDER BY products.id
SELECT ... FROM categories WHERE categories.id IN (...)

Вместо N дополнительных запросов SQLAlchemy делает один дополнительный запрос по набору внешних ключей.

joinedload и selectinload

Стратегия Как грузит Когда удобно
selectinload() отдельный SELECT ... WHERE id IN (...) универсальный выбор для списков и коллекций
joinedload() добавляет JOIN к основному запросу часто удобно для одиночной many-to-one связи
lazyload() грузит при первом доступе к атрибуту простые случаи, где связь может не понадобиться
raiseload() падает при незапланированной ленивой загрузке поиск скрытых N+1 в важных сценариях

Для учебного API используем selectinload(): он хорошо показывает намерение и не раздувает строки результата при коллекциях.

Фильтр по category_slug

CategorySlugParam = Annotated[
    str | None,
    Query(min_length=2, max_length=40),
]


@router.get("", response_model=list[ProductRead])
def list_products(
    session: SessionDep,
    search: SearchParam = None,
    limit: LimitParam = 10,
    category_slug: CategorySlugParam = None,
    only_available: bool = True,
) -> list[Product]:
    statement = (
        select(Product)
        .options(selectinload(Product.category))
        .order_by(Product.id)
    )

    if search:
        statement = statement.where(
            Product.title.ilike(f"%{search}%")
        )
    statement = statement.where(
        Product.is_available == only_available
    )
    if category_slug:
        statement = statement.join(Product.category).where(
            Category.slug == category_slug
        )

    return list(session.scalars(statement.limit(limit)))

Существующие search, limit и only_available остаются на месте. Меняется только фильтр категории: теперь он делает JOIN и сравнивает Category.slug. selectinload() отдельно загружает категорию для ответа.

JOIN не всегда означает загрузку relationship

join(Product.category)
  └─ помогает SQL-запросу фильтровать или сортировать строки

selectinload(Product.category)
  └─ говорит ORM заранее заполнить атрибут product.category

Это частая путаница. JOIN отвечает за SQL-условие, а loader option отвечает за состояние ORM-объекта после выполнения запроса.

Сортировка по категории

statement = (
    select(Product)
    .join(Product.category)
    .options(selectinload(Product.category))
    .order_by(Category.name, Product.title)
)

Когда нужно фильтровать или сортировать по связанной таблице, добавляем join(). Когда нужно вернуть связанную таблицу в ответе, добавляем стратегию загрузки.

Удаление категории

Если в категории есть товары, удаление должно быть осознанным бизнес-решением.

Вариант Поведение
запретить удаление вернуть 409 Conflict, если есть товары
перенести товары сначала назначить им другую категорию
удалить товары каскадом опасно для каталога, подходит не всем доменам

В Products API безопаснее начать с запрета удаления непустой категории.

Проверка перед удалением

from sqlalchemy import func


@router.delete("/{category_id}", status_code=status.HTTP_204_NO_CONTENT)
def delete_category(
    category_id: int,
    session: SessionDep,
    _admin: AdminRoleDep,
) -> None:
    category = get_category_or_404(category_id, session)

    products_count = session.scalar(
        select(func.count(Product.id)).where(
            Product.category_id == category.id
        )
    )
    if products_count:
        raise HTTPException(
            status_code=status.HTTP_409_CONFLICT,
            detail="Category contains products",
        )

    session.delete(category)
    session.commit()

Такой код явно говорит клиенту, почему операция невозможна. База остаётся последней линией защиты, но API не отдаёт наружу случайную ошибку драйвера.

        "/api/v1/products",
        json={
            "title": "Mechanical Keyboard",
            "category_id": electronics["id"],
            "price": 120.00,
        },
    )
    admin_client.post(
        "/api/v1/products",
        json={
            "title": "Clean Code",
            "category_id": books["id"],
            "price": 39.00,
        },
    )

    response = admin_client.get(
        "/api/v1/products?category_slug=electronics"
    )

    assert response.status_code == 200
    products = response.json()
    assert [product["title"] for product in products] == [
        "Mechanical Keyboard"
    ]

Фильтр проверяет не только SQLAlchemy-запрос, но и то, что API-контракт остался удобным для клиента.

Минимальный workflow

1. Добавить Category ORM-модель
2. Заменить Product.category на Product.category_id + relationship
3. Создать Alembic-миграцию
4. Аккуратно перенести старые category-строки в categories
5. Обновить ProductCreate, ProductUpdate и ProductRead
6. Добавить и подключить categories-роутер
7. Сохранить AdminRoleDep в изменяющих endpoints
8. Обновить POST, PUT, PATCH и фильтры товаров
9. Добавить selectinload для ответов со связями
10. Проверить alembic upgrade head, alembic check и pytest

Связь между таблицами затрагивает весь вертикальный срез: схему базы, ORM-модели, миграции, API-схемы, роутеры и тесты.

Практика

Задача: вынести категорию товара в отдельную таблицу и обновить Products API.

  1. Создайте ORM-модель Category с полями id, name и slug.
  2. Замените Product.category на Product.category_id и Product.category relationship.
  3. Добавьте обратную связь Category.products через back_populates.
  4. Создайте Alembic-миграцию для таблицы categories и внешнего ключа в products.
  5. Если в базе уже есть товары, перенесите старые строковые категории в новую таблицу.
  6. Добавьте схемы CategoryCreate и CategoryRead.
  7. Обновите ProductCreate: на входе используйте category_id.
  8. Обновите ProductUpdate, чтобы категорию можно было менять через PATCH.
  9. Обновите ProductRead: в ответе возвращайте вложенную category.
  10. Добавьте endpoints категорий, защитите изменяющие операции через AdminRoleDep и подключите роутер в create_app().
  11. Обновите POST, PUT и PATCH товаров для работы с category_id.
  12. В списке товаров добавьте фильтр category_slug, сохранив search, limit и only_available.
  13. Используйте selectinload(Product.category) в запросах, которые возвращают товары наружу.
  14. Проверьте миграцию на PostgreSQL: alembic upgrade head, заполнение старых товаров и ограничение NOT NULL.
  15. Проверьте сценарии создания товара, фильтрации по категории и попытки создать товар с несуществующей категорией.

Дополнительная задача: запретите удалять категорию, если в ней есть товары, и покройте этот сценарий тестом на 409 Conflict.

Итоги

На этой лекции мы научились:

  • понимать разницу между ForeignKey и relationship().
  • описывать many-to-one и one-to-many связи в SQLAlchemy 2.0.
  • использовать back_populates для двусторонней ORM-связи.
  • переводить строковое поле в отдельную таблицу через Alembic-миграцию.
  • отличать изменение схемы от переноса данных.
  • возвращать вложенные ORM-объекты через Pydantic from_attributes=True.
  • фильтровать товары по полям связанной таблицы через join().
  • избегать N+1 через selectinload().
  • проектировать безопасное удаление связанных данных.

На следующей лекции разберём транзакции глубже: атомарные операции, flush(), rollback, обработку IntegrityError и сценарии, где один HTTP-запрос меняет несколько таблиц сразу.
